# 설계 문서 작성

신규 시스템 또는 기능에 대한 구현 설계 문서를 작성하라.

사용자가 요구사항을 설명하면, 코드베이스를 분석하여 설계 문서를 `Docs/` 디렉토리에 마크다운 파일로 저장한다.

사용자 입력: $ARGUMENTS

## 절차

### 1단계: 요구사항 정리

사용자가 제시한 요구사항을 정리하라. `$ARGUMENTS`가 제공된 경우 이를 기능명 또는 요구사항으로 활용한다. 불명확한 부분이 있으면 질문하라.

### 2단계: 코드베이스 분석

요구사항과 관련된 기존 코드를 탐색하라:
- 연관 클래스의 헤더 및 구현 파일을 읽는다
- 기존 패턴, 컨벤션, 아키텍처를 파악한다
- 모듈 의존성 규칙(WxCore 외 플러그인 간 직접 의존 금지)을 확인한다

### 3단계: 설계 문서 작성

다음 구조로 `Docs/Plan_<기능명>.md` 파일을 작성하라:

````markdown
# <기능명> 설계 문서

## 개요
기능의 목적과 핵심 동작을 1~2문장으로 요약.

---

## 동작 사양
구체적인 동작 규칙을 표나 목록으로 정리.
공식이 있으면 명시.

---

## 실행 흐름
시스템의 실행 순서를 텍스트 다이어그램으로 표현.
```
시작
├─ 분기 A
│   └─ 처리
├─ 분기 B
│   └─ 처리
└─ 종료
```

---

## 클래스 설계
신규/수정 클래스별로 다음을 기술:
- 상속 구조
- 소속 모듈 및 근거
- 주요 프로퍼티 (표 형식)
- 핵심 구현 로직 (의사코드 또는 코드 스니펫)

---

## 기존 코드 수정
기존 파일을 수정해야 하는 경우, 파일별로 수정 위치와 변경 내용을 구체적으로 기술.

---

## 신규 Gameplay Tag
추가가 필요한 태그를 코드 형식으로 나열.

---

## 모듈 의존성
Build.cs 변경이 필요하면 명시.

---

## 작업 체크리스트

### 코드 작업
| # | 작업 | 파일 |
|---|------|------|
| 1 | ... | ... |

### 에디터 작업
| # | 작업 | 비고 |
|---|------|------|
| 1 | ... | ... |

---

## 고려 사항
멀티플레이어, 성능, 확장성 등 유의할 점.
````

### 작성 규칙

- **코드베이스 기반**: 기존 코드의 패턴과 컨벤션을 따른다. 추측하지 말고 실제 코드를 읽고 반영한다.
- **모듈 배치 근거**: 각 클래스가 어느 모듈에 속하는지, 왜 그 모듈인지 명시한다.
- **기존 코드 수정**: 기존 파일을 수정해야 하는 경우, 수정 위치와 내용을 구체적으로 기술한다.
- **실행 가능한 수준**: 설계 문서만으로 구현에 착수할 수 있을 정도로 구체적으로 작성한다.
- **불필요한 내용 배제**: 해당 기능과 관련 없는 섹션은 생략한다. (예: Gameplay Tag 추가가 없으면 해당 섹션 생략)

### 4단계: 결과 보고

설계 문서의 핵심 포인트를 간결하게 요약하여 사용자에게 보고하라.
