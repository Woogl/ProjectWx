# 모듈 코드 리뷰 문서 생성·갱신

프로젝트의 각 **플러그인/모듈**을 코드 리뷰해, 개발자·미래 세션이 **무엇을 고쳐야 하는지**를 심각도별로 정리한 리뷰 문서를 `Docs/Programmer/module_review_<Module>.md`로 만든다. `readme-writer`가 "이 모듈이 무엇인지"의 오리엔테이션 맵이라면, 이 스킬은 그 지도 위에서 "이 모듈의 무엇이 문제인지"를 짚는 액션 목록이다 — 두 스킬은 상보적이다.

핵심 원칙은 세 가지다.

1. **컨텍스트 폭발 방지** — 오케스트레이터(이 스킬을 실행하는 너)는 소스를 직접 통독하지 않는다. 모듈마다 **서브에이전트 1개**를 띄워 각자 자기 모듈만 읽고 리뷰 문서를 직접 쓰게 한다. 여러 모듈은 한 메시지에서 병렬로 띄운다.
2. **점진적 갱신** — 각 문서 끝에 보이는 provenance 라인으로 리뷰 시점 커밋 SHA를 노출한다. 재실행 시 그 SHA 이후 변경된 모듈만 골라 다시 리뷰한다.
3. **무수정 · 외부 문서 보존** — 이 스킬은 **소스를 절대 수정하지 않는다**(그래서 오케스트레이터에 `Write` 권한이 없고, 서브에이전트도 리뷰 문서 1개만 쓰고 소스는 손대지 않는다). 산출물은 리뷰 문서뿐이며, 실제 수정은 사람이 문서를 보고 판단해 별도로 한다. 또한 provenance 라인이 없는 기존 문서는 이 스킬의 산출물이 아니므로(수기 문서·다른 도구 결과) **foreign**으로 보고 자동으로 덮어쓰지 않는다.

---

## 1. 대상 결정 (인자 처리)

`Glob("Plugins/*/*.uplugin")`로 플러그인을, `Glob("Source/*/*.Build.cs")`로 소스 모듈(`WxGame` 등)을 동적으로 발견한다. 새 모듈·플러그인이 추가돼도 이 스킬을 고칠 필요가 없어야 한다. **런타임 모듈만 대상으로 한다** — descriptor의 모듈 `Type`이 `Runtime`이 아니면(예: `WxEditor`의 `Editor`) 대상에서 제외한다(인자로 명시해도 리뷰하지 않는다). `Type`은 플러그인이면 `.uplugin`, 소스 모듈이면 루트 `.uproject`의 `Modules[]`에 있다.

모듈 → 경로 / 문서 위치 매핑:

| 종류 | 분석 경로(소스) | 리뷰 문서 |
| --- | --- | --- |
| 플러그인 `<Name>` | `Plugins/<Name>` | `Docs/Programmer/module_review_<Name>.md` |
| 소스 모듈 `<Name>` | `Source/<Name>` | `Docs/Programmer/module_review_<Name>.md` |

리뷰 문서는 종류와 무관하게 **항상** `Docs/Programmer/module_review_<Name>.md`에 둔다(모듈 소스 밖 중앙 폴더 — 아침에 한 곳에서 전 모듈 리뷰를 훑을 수 있고, stale 판정도 단순해진다).

인자에 따라 대상 집합을 정한다.

- **인자 없음** (기본): `git rev-parse --short HEAD`로 현재 SHA를 구한 뒤, 각 모듈의 리뷰 문서 상태를 판정해 **missing 또는 stale인 모듈만** 대상으로 삼는다. fresh·**foreign**은 건너뛴다(foreign은 마무리 보고에 "외부 문서로 보존"으로 명시). 대상이 0개면 "모두 최신"이라고 보고한다.
- **모듈명 1개 이상** (예: `WxCombat`, `WxCombat WxInventory`): 그 모듈만 다시 리뷰한다(stale 여부와 무관하게 다시 씀). 단 대상 문서가 **foreign**(provenance 없는 외부 문서)이면 자동으로 덮어쓰지 말고, 그 사실을 경고한 뒤 덮어쓸지 사용자 확인을 받는다. 발견된 모듈 목록에 없는 이름이면 리뷰하지 말고, 유효한 모듈 목록을 한국어로 안내한다. 비런타임(에디터 전용) 모듈명이면 "에디터 전용이라 대상에서 제외" 한 줄로 안내하고 리뷰하지 않는다.
- **`all`**: 발견된 모든 모듈을 (stale 여부와 무관하게) 다시 리뷰하되, **foreign 문서는 건너뛰고** 보고한다(일괄 실행이 외부 문서를 파괴하지 않도록).

### 상태 판정 (missing / foreign / stale / fresh)

각 리뷰 문서 **끝**에는 다음 형식의 provenance 라인이 있다. 숨기지 않고 렌더링에 그대로 노출한다(독자가 문서가 어느 시점 기준인지 바로 알 수 있게):

```
*문서 기준 커밋 `<short-sha>` · 리뷰일 <YYYY-MM-DD> · 소스 <N>파일 — `/module-review`로 갱신*
```

판정 절차(모듈 경로 = 위 표의 "분석 경로", 문서 경로 = `Docs/Programmer/module_review_<Name>.md`):

1. 리뷰 문서 파일이 없으면 → **missing**.
2. `Grep`으로 `문서 기준 커밋` 라인을 찾는다.
   - 라인이 **없으면** → **foreign**. provenance가 없다는 것은 이 스킬의 산출물이 아니라는 뜻이다(수기 문서·다른 도구 결과). **stale로 보지 말고 보존한다**(자동 덮어쓰기 금지).
   - 라인이 있으면 `문서 기준 커밋` 바로 뒤 **첫 백틱 스팬**(`[0-9a-f]{7,40}` 패턴)을 `<sha>`로 읽는다. 같은 줄 끝의 `` `/module-review` `` 를 집지 않도록 첫 SHA 스팬만 취한다.
3. (provenance가 있을 때만) 아래 두 명령으로 **모듈 소스 변경**을 확인한다:
   - `git diff --name-only <sha> HEAD -- <모듈경로>`
   - `git status --porcelain -- <모듈경로>`
   둘 중 하나라도 변경이 있으면 → **stale**, 둘 다 비어 있으면 → **fresh**.
   - 단, `git diff`가 기록된 SHA를 못 찾아 실패하면(`fatal: bad object` 등 — 히스토리 재작성·squash·shallow clone) 변경 여부를 판정할 수 없으므로 **stale로 간주**해 다시 리뷰한다(에러로 중단하지 않는다).

> 리뷰 문서는 모듈 폴더 *밖*(`Docs/Programmer/`, `module_review_` 접두)에 있으므로, `readme-writer`와 달리 diff·status에서 문서 자신을 빼는 `:(exclude)` pathspec이 필요 없다 — `-- <모듈경로>` 한정만으로 문서 자신의 변경은 애초에 잡히지 않는다.

> 점진 갱신은 모듈 *소스 디렉터리* 변경만 본다. (1) `WxCore` 공용 정의(태그/Enum) 변경은 이를 인용하는 소비 모듈 경로 diff에 안 잡히고, (2) BP/WBP가 본체인 모듈(WxUI)의 에셋·덤프는 게임 루트 `Content/`·`Docs/AssetDump/`에 있어 모듈 경로 밖이다. 이런 파급이 의심되면 해당 모듈을 인자로 지정해 강제 재리뷰한다.

## 2. 모듈별 리뷰 서브에이전트 (병렬)

대상 모듈마다 **서브에이전트 1개**를 띄운다(`Agent`, subagent_type: `general-purpose`; 여러 모듈이면 한 메시지에 여러 호출로 병렬). 각 서브에이전트에 아래를 전달한다.

- 모듈명, 분석 경로, 리뷰 문서 경로(`Docs/Programmer/module_review_<Name>.md`)
- provenance 라인에 박을 **커밋 SHA**(현재 `git rev-parse --short HEAD` 값)와 **리뷰일**(오늘 날짜). 이 둘은 오케스트레이터가 확정해 넘긴다 — 서브에이전트는 git·날짜를 다시 조회하지 말고 받은 값을 그대로 쓴다. **소스 파일 수 `<N>`** 은 서브에이전트가 직접 센다(아래 작성 규칙의 카운트 기준).
- 아래 **리뷰 루브릭**, **리뷰 문서 템플릿**, **작성 규칙**

서브에이전트가 할 일:

1. **소스를 절대 수정하지 않는다.** 읽기·검색만 하고, 산출물은 리뷰 문서 **1개**를 `Write` 하는 것뿐이다.
2. 그 모듈의 `README.md`(`Plugins/<Name>/README.md` 또는 `Source/<Name>/README.md`)가 있으면 **먼저** 읽어 진입점·경계를 빠르게 잡는다(readme-writer 산출물, 없으면 건너뜀). 그 지도를 따라 `*.Build.cs`·`Public/`·`Private/` 헤더와 **핵심 로직(cpp)까지** 내려가 리뷰한다. 헤더만 훑지 말고 복잡·위험한 파일을 깊게 본다. **모든 파일을 통독하지 않는다** — 리뷰 가치가 높은 곳에 시간을 쓴다.
3. 아래 **리뷰 루브릭 5차원**으로 발견을 수집하고, 각 발견을 심각도(🔴 심각 / 🟡 개선 / 🟢 사소)로 분류한다.
4. 아래 템플릿에 맞춰 리뷰 문서를 **직접 `Write`** 한다. 끝의 provenance 라인은 받은 SHA·리뷰일을 그대로 박고 `<N>` 자리만 1에서 센 소스 파일 수로 채운다(라인 형식·문구는 변경 금지).
5. 마지막 메시지에 본문은 반환하지 말고(오케스트레이터 컨텍스트 절약) 한 줄만 반환한다: `DONE <모듈> · 🔴N 🟡M 🟢K · <가장 중요한 발견 한 줄>`. 오케스트레이터가 마무리 보고에서 이를 모은다.

### 리뷰 루브릭 (5차원)

발견은 아래 다섯 범주 중 하나로 분류한다. **고신호 우선** — 실질적 문제만 적고, 억지 발견이나 스타일 트집은 하지 않는다.

- **버그/정확성**: 널 역참조, 경쟁 상태, 객체 수명주기(댕글링·해제 후 사용), 잘못된 조건·로직, 미처리 에러·실패 경로.
- **설계/구조**: 과한 결합도, 모듈 경계 침범, 갓 클래스, 잘못된 리플리케이션 권한(서버/클라)·권위 모델, 상태 관리 결함.
- **규칙 위반**: 프로젝트 `CLAUDE.md`의 코딩/모듈 규칙에 대한 **구체적** 위반. 예: 플러그인이 `WxCore` 외 다른 Wx 플러그인 참조, `Wx` prefix 누락, 델리게이트 콜백의 `Handle` prefix 누락, override에서 `Super::` 미호출, `BlueprintCallable` 오용(BP Function Library/Async 팩토리 외), 불필요한 람다, 소스 첫 줄 Copyright 누락. **일반론적 "더 좋은 스타일" 훈수는 하지 않는다** — 명시된 규칙 위반만.
- **중복/복잡도**: 실질적 코드 중복, 데드 코드, 불필요하게 복잡한 제어 흐름.
- **성능/안전**: 명백한 성능 문제(핫패스의 불필요한 할당·복사·매 틱 탐색 등), 언세이프 캐스트·검증 없는 접근.

### 리뷰 문서 템플릿 (서브에이전트에 전달)

```
# <Module> — 코드 리뷰

> <1~2문장: 이 모듈 코드의 전반적 건강 인상. 그리고 이번 리뷰가 어디까지 봤는지 커버리지 한 줄.>

## 요약
| 심각도 | 개수 |
| --- | --- |
| 🔴 심각 | <N> |
| 🟡 개선 | <M> |
| 🟢 사소 | <K> |

## 결과

### 1. 🔴 <제목>
- **위치**: `<루트 기준 상대경로>:<라인>`
- **범주**: <버그/정확성 | 설계/구조 | 규칙 위반 | 중복/복잡도 | 성능/안전>
- **문제**: <무엇이 왜 문제인지 — 가능하면 구체적 실패 시나리오나 근거>
- **제안**: <어떻게 고칠지, 간결하게>
- **확신도**: <높음 | 중간 | 낮음(의도된 설계일 수 있음)>

### 2. 🟡 <제목>
<위와 동일 항목>

### 3. 🟢 <제목>
<위와 동일 항목>

## 검토 범위
- **깊게 본 파일**: `<경로>`, `<경로>` …
- **훑은 파일**: `<경로>` …
- **미검토 / 한계**: <시간·복잡도로 깊이 못 본 부분을 정직하게. 없으면 "없음">

---
*문서 기준 커밋 `<SHA>` · 리뷰일 <DATE> · 소스 <N>파일 — `/module-review`로 갱신*
```

발견에는 심각도 높은 순(🔴→🟡→🟢)으로 정렬해 `1`부터 이어지는 일련번호를 매기고, 심각도는 번호 뒤 이모지(🔴/🟡/🟢)로 표시한다. 발견이 없는 심각도의 항목은 통째로 생략하며, 번호는 실제 존재하는 발견에만 1부터 빈틈 없이 이어 매긴다.

**작성 규칙** (서브에이전트에 함께 전달):

- 대상 독자는 **이 코드를 고칠 개발자/미래 세션**이다. 리뷰 문서는 "무엇을 왜 고쳐야 하는가"의 **액션 목록**이지, 코드 설명서가 아니다. 간결하고 실행 가능하게.
- **고신호 우선.** 실질적 문제만 적는다. 🟢 사소는 정말 볼 가치가 있을 때만 넣고, 개수를 채우려 억지로 만들지 않는다. 모듈이 깨끗하면 **깨끗하다고 정직히** 적는다(발견 0개도 정상 결과다).
- **검증된 사실만.** 모든 발견에 `파일:라인` 근거를 붙인다. 추측으로 발견을 만들지 않는다. 파일 경로·타입명·라인은 실제와 정확히 일치해야 한다.
- **중립성 존중.** 특이한 패턴이 곧 버그는 아니다 — 의도된 설계일 수 있다. 확신이 안 서면 확신도를 "낮음(의도된 설계일 수 있음)"으로 두고, 단정하지 말고 근거와 함께 제시해 사람이 판단하게 한다.
- **규칙 위반 범주는 `CLAUDE.md`가 권위다.** 프로젝트 `CLAUDE.md`의 코딩/모듈 규칙에 대한 구체적 위반만 이 범주로 적는다(일반론적 스타일 훈수 금지).
- 끝의 provenance 라인은 숨기지 말 것. SHA·리뷰일은 받은 값 그대로 쓰고(재계산 금지) `<N>` 자리만 채운다. 본문은 **한국어 평서체**(~한다/~이다). 타입명·함수명·경로·Gameplay Tag 등 식별자는 **영문 원문** 유지.
- provenance의 `<N>`(소스 파일 수)은 `<모듈경로>` 아래의 `*.h`/`*.cpp` 개수만 센다(레이아웃 비의존 — 플러그인은 `Plugins/<Name>/Source/...`, 소스 모듈은 `Source/<Name>/...`에 파일이 있다) — `Intermediate/`·`*.gen.cpp`·`*.generated.h`(빌드 산출물)는 제외한다.
- 모든 파일 경로는 저장소 루트(`C:\Wx`) 기준 상대경로로 적어 클릭 가능하게 한다.
- BP/WBP 내부 구조(위젯 계층·MVVM 바인딩·이벤트 그래프)는 이 리뷰의 범위 밖이다(C++ 코드에 집중). BP 디폴트값·구조가 리뷰에 꼭 필요하면 `Docs/AssetDump/`의 JSON 덤프를 참조하되(카테고리·범위는 `Docs/AssetDump/README.md`, 갱신은 `/dump-assets`), 발견은 C++ 근거로 적는다.

## 3. 마무리 보고 (아침 다이제스트)

한국어로 짧게 보고한다. 사용자가 아침에 한눈에 "어디에 불이 났는지" 보게 하는 것이 목표다.

- **다이제스트 표**: 이번에 생성·갱신한 모듈을 아래 표로 낸다. 서브에이전트 `DONE`의 심각도 카운트를 모으고, 문서 경로를 클릭 가능한 링크로 건다. 🔴가 많은 모듈이 위로 오게 정렬한다.

  | 모듈 | 🔴 | 🟡 | 🟢 | 문서 |
  | --- | --- | --- | --- | --- |
  | `WxCombat` | 2 | 5 | 3 | `Docs/Programmer/module_review_WxCombat.md` |

- **분류**: **생성**(missing→신규) / **갱신**(stale→재리뷰) / **건너뜀(fresh)** 모듈을 각각 나열. **보존(foreign)** — provenance가 없어 건드리지 않은 외부 문서가 있으면 모듈명과 함께 명시(예: `<Module> — 외부 문서로 보존, 덮어쓰려면 모듈명을 직접 지정`).
- **가장 중요한 발견 몇 개**를 서브에이전트 `DONE` 한 줄에서 뽑아 최상단에 요약한다(전체 발견을 산문으로 다시 풀지 않는다 — 상세는 각 문서에 있다).
- 대상 0개면 "모두 최신", 유효하지 않은 모듈명 입력이 있으면 유효 목록 안내, 서브에이전트가 `DONE`을 반환하지 않은 모듈이 있으면 실패로 표기.
- **맺음(한 줄)**: 이 스킬은 아무 소스도 수정하지 않았고 **리뷰 문서만** 냈다는 점, 발견은 코드 근거 기반이라 런타임 데이터(DataTable/BP)·의도된 설계까지는 단정 못 하므로 확신도 "낮음" 항목은 사람이 판단해야 한다는 점을 한 줄로 덧붙인다.
