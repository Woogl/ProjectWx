# 기획서 → 구현 체크리스트

지정한 **기획서** 하나를 읽고, 프로그래머가 "이 기획을 구현하려면 무슨 작업이 필요한가"를 한눈에 잡을 수 있는 **예상 작업 목록**을 `Docs/Programmer/checklist_<Title>.md`로 만든다. 이 체크리스트는 이후 워크플로우(기획서 → 체크리스트 → plan mode 설계 → worklog → 구현)의 앞단 재료다.

핵심 원칙 세 가지.

1. **작업 목록이지 설계서가 아니다** — 각 항목은 "무엇을 해야 하는가"와 그 **기획 근거**까지만 적는다. 클래스 구조·매크로·수치 계산식·코드 같은 **구체적 구현 방법은 쓰지 않는다**. 그건 구현 단계에서 정한다.
2. **기획서 중심, 코드를 뒤지지 않는다** — 소스를 grep하지 않는다(그래서 가볍고 서브에이전트도 쓰지 않는다). 아래 **작업 종류 카탈로그**(이 프로젝트의 구현 축)에 비춰 기획을 분해할 뿐, 기존 클래스가 실제로 있는지 단정하지 않는다.
3. **기획 공백을 짚는다** — 구현에 필요한데 기획서가 비워 둔 것(미정 수치, 모호한 규칙, "추후" 항목)은 지어내지 말고 **열린 질문**으로 모은다. 이게 프로그래머에게 가장 유용하다.

---

## 1. 대상 결정 (인자 처리)

인자 = 변환할 **기획서 파일명**(경로·부분명 가능, 확장자 생략 허용).

- **인자 없음**: 무엇을 변환할지 추측하지 말고 한국어로 되묻는다(이 스킬은 인자 없이 진행하지 않는다).
- **인자 있음**: `Glob`으로 `Docs/CombatDesign/**`·`Docs/Leveldesign/**`에서 매칭한다(이 두 폴더가 기획서의 위치다).
  - **정확히 1개** → 그 파일로 진행.
  - **0개** → 두 폴더의 `.md` 목록을 제시하며 어느 기획서인지 되묻는다.
  - **2개 이상** → 매칭된 후보를 나열하며 어느 것인지 되묻는다.
- **비마크다운만 매치**(`.docx`/`.pptx` 등): `Read`로 열 수 없으므로, 사실을 알리고 마크다운(`.md`) 기획서를 달라고 한다.
- **출력 파일명**: 내용을 반영한 간결한 영문 `Title_Case_With_Underscores`로 `Docs/Programmer/checklist_<Title>.md`를 정한다(예: `그로기_피니시_시스템_기획서` → `Docs/Programmer/checklist_Groggy_Finish.md`). 기존 `Docs/Programmer/` 산출물이 전부 영문이라 일관을 맞춘다.

---

## 2. 읽기 & 작업 분해

1. `Read`로 기획서 **전문**을 읽는다.
2. 기획을 1~2문장으로 요약하고, 걸치는 **도메인**을 판별한다(전투·UI·월드·인벤·AI·사운드·세이브 등). 애매하면 각 모듈 루트의 `README.md`(담당/경계 정리됨)를 가볍게 참조한다 — 무거운 코드 스캔이 아니다.
3. 기획서의 규칙·수치·플로우·상태표·예외 처리(전투 기획), 또는 구성 요소·설정 항목·동작 방식(레벨 기획)을 훑으며, **각 요구사항을 작업 항목으로** 옮긴다. 아래 **작업 종류 카탈로그**를 축으로 삼아 도메인/카테고리별로 묶는다.
4. **신규/기존을 단정하지 않는다** — 코드를 안 보므로 "기존이 있으면 재사용" 정도로만 부드럽게 적는다.
5. **각 항목은 한 줄**: `무엇을 · 기획 근거(절 번호나 항목명)`. 구현 방법은 넣지 않는다.
6. 구현에 필요하지만 기획서에 없는 것은 **열린 질문**으로 따로 모은다.

### 작업 종류 카탈로그 (분해의 축)

이 프로젝트에서 기획 하나가 보통 분해되는 작업 종류다. **도메인·대략 위치·명명**까지만 참고하고(구현 방법은 여기서도 쓰지 않는다), 기획에 해당하는 종류만 골라 항목을 만든다.

| 작업 종류 | 도메인 / 대략 위치 | 명명 | 판단 힌트 |
|---|---|---|---|
| GameplayAbility(능력·공격·반응) | WxCombat `AbilitySystem/Ability` · 게임 고유는 WxGame · 에셋 `Content/AbilitySystem/Ability` | `UWxAbility_X` / `GA_X` | 기존 능력 종류로 표현되면 BP+데이터만, 새 메커니즘이면 신규 |
| GameplayTag(상태·이벤트 식별) | **WxCore 한 곳** `WxGameplayTags.{h,cpp}` | `State.*`·`Event.*`·`Gimmick.*`·`Ability.*` 등 | ini 없이 100% C++ 네이티브. `UI.Layer/Action`은 CommonUI 문자열 태그 예외 |
| GameplayEffect(피해·버프·상태이상·코스트·쿨다운) | WxCombat `AbilitySystem/Effect` | `WxEffect_`·`WxMMC_`·`WxExecCalc_`, 드물게 `GE_` | 대개 **수치는 데이터테이블 행**, 새 상태이상·로직만 신규 |
| Attribute(스탯 축) | WxCombat `AbilitySystem/Attribute` + `DT_CharacterAttribute` | — | 새 스탯 축이면 속성 추가, 값 튜닝은 데이터 |
| DataTable 행/열 | WxCombat `FWx*Row` + `Content/AbilitySystem/DT_*` | `FWx*Row` / `DT_*` | 행 추가(가장 흔함)·열 추가·테이블 신규 |
| InputAction(입력) | `Content/Input/Actions/IA_*` + IMC | `IA_X` | 어빌리티 CDO가 IA를 직접 참조. 필요 IA가 있으면 배선만 |
| 애니메이션(몽타주+타이밍) | 몽타주 `Content/…/AM_*` · 노티파이 WxCombat `AnimNotify` | `AM_X` / `WxAnimNotify(State)_X` | 기존 타이밍 훅이면 몽타주에 배치만 |
| UI(위젯+뷰모델) | 베이스 WxUI · 게임 VM은 WxGame `MVVM` · 에셋 `Content/UI/Widget/WBP_*` | `WBP_X` / `UWxViewModel_X` | ASC 순수 표시=WxUI, 빙의 Pawn 등 게임 상태 의존=WxGame |
| 월드 오브젝트/기믹 | WxWorld(`AWxGimmick`) · 조립은 WxGame `WorldObject` | — | 상호작용·스포너블/기믹 구분, 권위 State + 세이브 복원 |
| 크로스 도메인 배선 | 계약·태그는 WxCore · 실제 배선은 WxGame(Resolver/GameMode) | `WxViewModelResolver_X` 등 | 여러 도메인이 얽히면 태그/인터페이스로 발행, 배선은 WxGame |

## 3. 문서 작성

아래 템플릿에 맞춰 `Docs/Programmer/checklist_<Title>.md`를 `Write`한다. `<...>` 자리를 채우고, 해당 없는 카테고리 섹션은 통째로 지운다.

**덮어쓰기 보호**: 대상 파일이 이미 있으면 먼저 `Read`한다. 끝에 아래 provenance 라인이 있는(이 스킬이 만든) 문서면 그대로 갱신하고, provenance가 없는 **수기·외부 문서**면 자동으로 덮어쓰지 말고 사실을 알린 뒤 사용자 확인을 받는다.

```
# <기획명> — 구현 체크리스트

> `<기획서 상대경로>` 기준의 **예상 작업 목록**이다. 구체적 구현 방법·로직·수치 설계는 담지 않는다 — 실제 설계는 구현 단계(plan mode·worklog)에서 정한다.

## 개요
<기획 1~2문장 요약 + 걸치는 도메인>

## 작업 목록

### <도메인/카테고리 (예: 전투 — 어빌리티)>
- [ ] <작업 항목> — <무엇을 · 기획 근거>
- [ ] ...

### <데이터/에셋>
- [ ] ...

## 열린 질문 / 기획 공백
- <구현에 필요하지만 기획서에 안 정해진 것>

---
*`<기획서 상대경로>` 기준 · 생성일 <YYYY-MM-DD> — `/design-checklist`로 갱신*
```

**작성 규칙**:

- 대상 독자는 **이 기획을 구현할 프로그래머**다. 체크리스트는 "무엇을 해야 하는가"의 목록이지 코드 설명서가 아니다. 간결하게.
- **구현 방법 금지.** 클래스 상속 구조·함수 시그니처·매크로·수치 계산식·코드 조각을 적지 않는다. 항목은 작업 단위(무엇을)와 기획 근거에서 멈춘다.
- **기획서에 있는 것만.** 추측으로 항목을 만들지 않는다. 근거가 없는 것은 "열린 질문"으로 돌린다.
- **도메인/카테고리로 그룹핑.** 위 카탈로그의 축을 쓰되, 기획에 없는 종류의 섹션은 만들지 않는다.
- 본문은 **한국어 평서체**(~한다/~이다). 타입·태그·경로 등 **식별자는 영문 원문** 유지.
- 파일 경로는 저장소 루트(`C:\Wx`) 기준 상대경로로 적어 클릭 가능하게 한다.
- provenance 라인의 생성일은 현재 세션의 오늘 날짜를 쓴다. 라인은 숨기지 않는다.

---

## 4. 마무리 보고

한국어로 짧게 보고한다.

- 생성/갱신한 **문서 경로**와 기획 **핵심 한 줄**.
- **도메인 분포**(예: 전투·UI·월드), **작업 항목 수**, **열린 질문 수**.
- 자동 생성물이므로 사용자가 열어 검토하고, 다듬을 방향(항목 세분화·특정 도메인 보강 등)을 알려주면 같은 스킬로 재생성하면 된다고 한 줄 안내.
