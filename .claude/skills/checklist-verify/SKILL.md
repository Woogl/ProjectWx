# 체크리스트 ↔ 코드 대조 점검

`design-checklist`가 만든 체크리스트(`Docs/Programmer/checklist_*.md`)를 **실제 코드·에셋과 대조**해, **각 작업 항목에 판정(✅⚠️❌❓)을 직접 채우고** 주목할 **특이사항만** 문서 뒤에 덧붙인다. `design-checklist`가 코드를 안 보고 기획을 작업 목록으로 뽑는다면, 이 스킬은 그 목록을 코드와 맞대어 **두 방향의 어긋남**을 잡는다 — 기획이 앞선 **미구현**과, 코드가 앞선 **기획서 미최신화**.

핵심 원칙 세 가지.

1. **소스 무수정** — 이 스킬은 **소스 코드를 절대 수정하지 않는다**(읽기·검색만). 쓰는 것은 대상 체크리스트 문서 하나뿐이다 — 각 항목에 판정을 기입하고, 특이사항 섹션을 덧붙인다. 실제 조치(구현·기획서 갱신)는 사람이 결과를 보고 별도로 한다.
2. **컨텍스트 격리** — 오케스트레이터(이 스킬을 실행하는 너)는 소스를 통독하지 않는다. **서브에이전트 1개**를 띄워 그가 코드·에셋을 대조하고 문서를 갱신하게 하며, 본문이 아니라 요약만 돌려받는다.
3. **항목에 직접 + 특이사항만** — 판정은 원본 작업 항목의 불릿에 **인라인으로 채운다**. ✅(정상 구현)는 인라인으로 끝내고, 주목할 것(⚠️ 불일치·❌ 미구현·➕ 기획 외·❓ 확인 불가)만 문서 뒤 "## 점검 특이사항"으로 모은다. 원본의 항목 텍스트·근거·열린 질문·생성 provenance 라인은 **보존**한다(판정 이모지로 불릿만 바꾼다).

---

## 1. 대상 결정 (인자 처리)

인자 = 점검할 **체크리스트명 또는 기획서명**(부분명 가능).

- **인자 없음**: 무엇을 점검할지 추측하지 말고 한국어로 되묻는다.
- **인자 있음**: `Glob`으로 `Docs/Programmer/checklist_*<인자>*.md`를 매칭한다.
  - **정확히 1개** → 그 파일로 진행.
  - **0개** → `Docs/Programmer/checklist_*.md` 목록을 제시하며 되묻는다. 목록 자체가 비면 "먼저 `/design-checklist <기획서>`로 체크리스트를 만들라"고 안내한다.
  - **2개 이상** → 매칭된 후보를 나열하며 되묻는다.

---

## 2. 점검 기준값 확정

오케스트레이터가 아래를 구해 서브에이전트에 넘긴다. 서브에이전트는 이 값을 재조회하지 말고 받은 값을 그대로 쓴다.

- **커밋 SHA**: `git rev-parse --short HEAD`.
- **점검일**: 현재 세션의 오늘 날짜.

---

## 3. 대조 서브에이전트 (1개)

`Agent`(subagent_type: `general-purpose`)를 **1개** 띄운다. 대상 체크리스트 **경로**, 2절의 **SHA·점검일**, 아래 **찾는 법·판정 카테고리·인라인 표기·특이사항 템플릿·작성 규칙**을 전달한다.

서브에이전트가 할 일:

1. 체크리스트를 `Read`하고, 각 작업 항목에서 **검색 키워드**(클래스·태그·컴포넌트·에셋명)를 뽑는다.
2. 각 항목을 코드·에셋과 대조해 아래 **판정 카테고리**로 분류한다.
3. **인라인 기입** — 원본 각 항목의 불릿을 판정 이모지로 바꾼다(`- [ ] <항목>` → `- ✅ <항목>` 등). **항목 텍스트와 근거는 그대로 두고 불릿만 바꾼다.** (원본이 이미 판정 이모지 상태면 새 판정으로 갱신.)
4. **특이사항 별첨** — ⚠️·❌·➕·❓만 문서 뒤 "## 점검 특이사항" 섹션에 상세로 적는다. **✅는 인라인으로 끝내고 여기 반복하지 않는다.** `➕`(기획 외 구현)는 원본 항목에 없으니 이 섹션에만 적는다. 기존 점검 섹션("## 점검 특이사항" 또는 옛 "## 점검 결과")이 있으면 그 블록을 새 것으로 교체한다.
5. **소스를 수정하지 않는다.** 원본의 "열린 질문 / 기획 공백"과 생성 provenance 라인은 건드리지 않는다.
6. 마지막 메시지에 본문은 반환하지 말고 **한 줄만** 반환한다: `DONE <경로> · ✅N ⚠️M ❌K ➕J ❓P · <가장 중요한 갭 한 줄>`.

### 찾는 법 (코드 + 에셋 존재 확인)

- **도메인 진입점**: 항목의 도메인이 애매하면 해당 모듈 루트의 `README.md`(담당/경계·핵심 타입 정리)를 먼저 읽어 어디를 볼지 잡는다.
- **C++**: `Grep`/`Read`로 클래스·함수·태그 선언의 존재와 대략적 동작을 확인한다. 명명 힌트 — 어빌리티 `UWxAbility_*`, 이펙트 `WxEffect_/WxMMC_/WxExecCalc_`, 태그는 `Plugins/WxCore/.../WxGameplayTags.h` 한 곳, AI는 `WxBT*`·`UWxAIPerceptionComponent`·`UWxPatrolComponent`.
- **에셋**: `Content/`에서 `Glob`으로 파일 **존재**만 확인한다 — 어빌리티 `GA_*`, 몽타주 `AM_*`, 입력 `IA_*`, 데이터테이블 `DT_*`, 위젯 `WBP_*`. **내부 값(DT 행 수치·BP 노드·BT 그래프·몽타주 노티파이 배치)은 이 스킬의 범위가 아니다** — 존재만으로 판정이 안 되면 `❓`로 두고 무엇을 확인해야 하는지 적는다.
- **미구현 단정 금지**: 못 찾은 것과 진짜 없는 것을 구분한다. 명명이 달라 놓쳤을 수 있으면 확신도를 낮추고 단정하지 않는다.

### 판정 카테고리

| 판정 | 뜻 | 방향 |
|---|---|---|
| ✅ 구현 확인 | 항목이 코드/에셋에 존재 | — |
| ⚠️ 불일치/부분 | 코드가 있으나 기획과 다르거나 일부만 구현 | 코드가 앞섬(기획서 미최신 의심) |
| ❌ 미구현 | 체크리스트에 있으나 코드/에셋에 없음 | 기획이 앞섬 |
| ➕ 기획 외 구현 | 체크리스트/기획엔 없는데 관련 구현이 코드에 있음 | 코드가 앞섬(기획서 미최신) |
| ❓ 확인 불가 | 에셋 내부·런타임 데이터라 존재 확인만으론 판정 어려움 | — |

### 인라인 판정 표기 (작업 목록에 직접)

원본 작업 목록의 불릿(`- [ ] …`)을 판정 이모지로 바꾼다. 마크다운 체크박스 문법 대신 이모지 불릿을 쓴다.

```
### <도메인/카테고리>
- ✅ <항목 그대로> (근거절) — <원본 근거 유지>
- ⚠️ <항목 그대로> (근거절) — <원본 근거 유지>
- ❌ <항목 그대로> (근거절) — <원본 근거 유지>
- ❓ <항목 그대로> (근거절) — <원본 근거 유지>
```

- 항목 텍스트·괄호 근거·"— 설명"은 **원본 그대로**. 바꾸는 것은 앞의 불릿뿐이다.
- 상세 검증 근거(경로:라인·확신도)는 인라인에 늘어놓지 말고 ⚠️·❌·❓면 아래 특이사항 섹션에 적는다. ✅는 인라인으로 끝.

### 점검 특이사항 템플릿 (문서 뒤에 추가)

```
## 점검 특이사항

> 커밋 `<sha>` · 점검일 <YYYY-MM-DD> · ✅<N> ⚠️<M> ❌<K> ➕<J> ❓<P>. 코드·에셋 존재 대조 기반이라 런타임 데이터(DataTable 값·BP/BT 내부)·의도된 미구현까지는 단정하지 못한다.

- ⚠️ **<항목>** — <코드가 기획과 어떻게 다른지> · 확신도 <높음/중간/낮음> · <근거: 경로:라인 또는 에셋 경로>
- ❌ **<항목>** — <어디를 봤는데 없었는지> · 확신도 <…>
- ➕ **<기획 외 발견>** — <코드에 있으나 체크리스트/기획에 없음> · <근거>
- ❓ **<항목>** — <무엇을 확인해야 하는지> · <근거>

### 기획-코드 갭 (조치 제안)
- **기획서 최신화 필요**: <⚠️·➕에서 기획서가 코드를 못 따라간 항목 몇 줄>
- **구현 필요**: <❌ 중 실제로 만들어야 할 항목 몇 줄>

---
*점검 커밋 `<sha>` · 점검일 <YYYY-MM-DD> — `/checklist-verify`로 갱신*
```

- ✅는 특이사항에 넣지 않는다(인라인 판정으로 충분). 발견이 없는 판정은 통째로 생략한다. 상세는 ⚠️→❌→➕→❓ 순으로 묶는다.

### 작성 규칙 (서브에이전트에 함께 전달)

- 대상 독자는 **이 기능을 구현·정리할 개발자**다. 항목별 판정으로 현황을 한눈에 보이고, 특이사항으로 "무엇이 어긋났고 무엇을 확인해야 하는가"를 짚는다. 간결하게.
- **검증된 사실만.** 특이사항의 모든 판정에 근거(경로:라인 또는 에셋 경로)를 붙인다. 근거 없이 판정하지 않는다.
- **중립성.** 코드 대조로는 런타임 데이터·의도된 설계까지 알 수 없다. 애매하면 확신도를 낮추고 `❓`로 두며 단정하지 않는다.
- **소스 무수정.** 산출물은 대상 체크리스트 문서뿐이다(인라인 판정 + 특이사항 섹션). 다른 파일은 읽기만 한다.
- 본문은 **한국어 평서체**. 타입·태그·경로 등 **식별자는 영문 원문** 유지. 파일 경로는 저장소 루트(`C:\Wx`) 기준 상대경로.
- 끝의 점검 provenance 라인은 숨기지 말고, 받은 SHA·점검일을 그대로 쓴다.

## 4. 마무리 보고

한국어로 짧게 보고한다.

- 갱신한 **문서 경로**와 **판정 분포**(✅N ⚠️M ❌K ➕J ❓P).
- **특이사항 핵심** — 서브에이전트 `DONE` 한 줄과 특이사항에서 뽑아, "기획서 최신화 필요" vs "구현 필요"로 나눠 최상단에 요약(전체를 산문으로 다시 풀지 않는다 — 상세는 문서에 있다).
- 이 스킬은 소스를 수정하지 않았고 체크리스트 문서에만 판정을 채웠다는 점, 확신도 낮은 항목(❓ 포함)은 사람이 판단해야 한다는 점을 한 줄로 덧붙인다.
