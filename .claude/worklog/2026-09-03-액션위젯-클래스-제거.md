# WxActionWidget 클래스 제거 + 클래스 리다이렉트

## 계획

### 목표
`UWxActionWidget` 은 09-01 에 `GetIcon()` override 를 걷어낸 뒤 본문이 빈 껍데기만 남았고, 모듈 리뷰(`Docs/Programmer/module_review_WxUI.md` 발견 6)도 데드 코드로 지목했다. 그때 클래스를 남긴 이유는 3개 WBP 가 이 클래스의 위젯 인스턴스를 물고 있어서였는데, CoreRedirects 로 그 참조를 부모인 엔진 `UCommonActionWidget` 으로 넘겨 애셋을 온전히 둔 채 클래스를 없앤다.

### 수정 범위
| 파일 | 수정할 내용 | 구분 |
|---|---|---|
| `Plugins/WxUI/Source/WxUI/Public/Widget/WxActionWidget.h` | 파일째 제거 | 삭제 |
| `Config/DefaultEngine.ini` | `[CoreRedirects]` 섹션 신설, `ClassRedirects` 한 줄 추가 | 수정 |

### 접근 방식
- **부모 클래스로 리다이렉트**: `UWxActionWidget` 은 `UCommonActionWidget` 에 아무것도 더하지 않으므로 부모로 넘기면 동작이 그대로다. `WBP_Button` 의 `InputActionWidget` 은 `UCommonButtonBase` 의 `BindWidgetOptional` 프로퍼티(타입 `UCommonActionWidget`)라 바인딩도 성립한다.
- **리다이렉트는 상주**: 애셋을 리세이브해 참조를 굳히고 ini 를 걷어낼 수도 있지만, 히스토리의 옛 애셋까지 커버하려면 한 줄을 남기는 편이 안전하고 비용도 없다.
- **코드 참조 없음**: 저장소에서 이 이름을 참조하는 소스는 헤더 자신뿐이다(나머지는 worklog·리뷰 문서와 생성 코드). 전용 빌드 의존은 09-01 에 이미 정리됐다.

## 완료

### 수정한 파일
| 파일 | 수정한 내용 | 구분 |
|---|---|---|
| `Plugins/WxUI/Source/WxUI/Public/Widget/WxActionWidget.h` | 빈 클래스 선언뿐이라 파일째 제거 | 삭제 |
| `Content/UI/Widget/WBP_Button.uasset`·`WBP_GameHUD.uasset`·`WBP_PlayerSkills.uasset` | 리다이렉트를 태운 채 리세이브해 액션 위젯 참조를 엔진 클래스로 굳힘 | 수정(에디터, 사용자 수행) |
| `Config/DefaultEngine.ini` | 리세이브용 `[CoreRedirects]` 섹션을 넣었다가 목적을 다해 제거 — 최종 diff 없음 | 변화 없음 |

### 구현·결정과 그 이유
- **부모로 넘기는 리다이렉트**: 지운 클래스가 부모에 아무것도 더하지 않았으므로 부모를 새 이름으로 지정하면 애셋이 물고 있던 위젯이 그대로 살아난다. 버튼 쪽 바인딩도 프로퍼티 타입이 부모라 영향이 없다.
- **리다이렉트는 일회용**: 애셋 3개를 리세이브해 참조를 굳힌 뒤 ini 를 걷어냈다. 옛 커밋의 애셋을 대비해 남겨두는 안도 있었지만, 설정에 영구 부채를 두지 않는 쪽을 택했다. 다시 필요해지면 같은 한 줄을 되살리면 된다.
- **끊긴 것을 눈이 아니라 패키지로 확인**: 리세이브 후 세 애셋의 import 테이블을 직접 뜯어 옛 클래스 참조가 하나도 없음을 확인했다. 두 애셋에 이름이 남아 보이는 건 위젯 인스턴스의 *이름*(디자이너 자동 명명)일 뿐 클래스가 아니며, 클래스는 모두 엔진 것으로 바뀌어 있었다.

### 계획 대비 달라진 점
- 계획은 ini 한 줄을 상주시키는 것이었으나, 리세이브로 참조가 정리된 것을 확인한 뒤 걷어냈다.

### 후속 과제
- `WBP_GameHUD`·`WBP_PlayerSkills` 의 액션 위젯 이름이 옛 클래스명 그대로다(동작 무해). 바꾸려면 바인딩·뷰모델 참조를 함께 봐야 한다.
- 소스 파일이 하나 줄었으므로 VS 솔루션을 쓴다면 `/generate-project-files` 로 갱신한다.
