# ActivateAbility BT Task 의 동기 종료 어빌리티를 Succeeded 로 보고

## 계획

### 목표
`module_review_WxAI.md` 이슈 4. `UWxBTTask_ActivateAbility::ExecuteTask` 는 `TryActivateAbility` 가 true 를 반환해도 그 안에서 어빌리티가 이미 끝났으면(즉발 버프, 몽타주 없는 원샷 등) `ActiveSpec->IsActive()` 가 false 라 Failed 를 반환한다. 무한 InProgress 고착을 막으려는 방어인데 정상 완료된 즉발 어빌리티까지 "실패" 로 뭉뚱그려, Sequence 배치에선 후속 노드가 실행되지 않고 Selector 배치에선 불필요한 폴백이 발동한다. 동기 종료라도 정상 완료면 Succeeded 로 보고한다.

원인은 순서다. `TryActivateAbility` **이후에** `OnAbilityEnded` 를 바인드하므로 발동 도중 지나간 종료 통지를 받을 방법이 없고, "비활성" 이라는 사실만 남아 정상 종료와 캔슬을 구분할 수 없다.

### 수정 범위
| 파일 | 수정할 내용 | 구분 |
|---|---|---|
| `Plugins/WxAI/.../WxBTTask_ActivateAbility.h` | 발동 구간 표시 플래그 + 동기 종료 결과 멤버 추가 | 수정 |
| `Plugins/WxAI/.../WxBTTask_ActivateAbility.cpp` | 델리게이트를 발동 전에 바인드, 동기 종료 결과를 ExecuteTask 가 반환 | 수정 |

### 접근 방식
- **바인드를 `TryActivateAbility` 앞으로 옮긴다.** 후보 루프에서 `TryActivateAbility` 직전에 `ActivatedHandle` 을 세워 콜백 필터가 동작하게 하고, 실패하면 되돌린다.
- **발동 구간의 통지는 `FinishLatentTask` 대신 멤버로 받는다.** ExecuteTask 가 아직 InProgress 를 반환하기 전이라 그 자리에서 `FinishLatentTask` 를 부르면 안 된다. `bIsActivating` 이 true 인 동안 콜백은 결과만 `ActivationResult` 에 적고 빠지며 ExecuteTask 가 그 값을 반환한다.
- **`ActivationResult` 의 미종료 표현은 `EBTNodeResult::InProgress`.** 별도 optional 없이 열거형이 이미 "아직 안 끝남" 을 표현한다. 노드 인스턴스가 재사용되므로 ExecuteTask 진입 때 초기화한다.
- **고착 방어는 남긴다.** 통지 없이 비활성인 예외 상황은 여전히 Failed 로 마감하되, 이제 이 경로는 "통지가 아예 오지 않은 경우" 로 좁혀진다.
- **`AbortTask`·`CleanUp` 은 손대지 않는다.**

### 엔진 코드 확인 (UE 5.8 GameplayAbilities)
1. **동기 종료해도 `TryActivateAbility` 는 true 다.** `InternalTryActivateAbility` 는 `CallActivateAbility` 를 부른 뒤 무조건 `return true`. 즉 "true 인데 비활성" 은 정상 완료를 포함한다.
2. **발동 도중 종료도 `OnAbilityEnded` 를 정상 브로드캐스트한다.** `EndAbility` → `NotifyAbilityEnded` → `OnAbilityEnded.Broadcast(FAbilityEndedData(Ability, Handle, false, bWasCancelled))`. 핸들과 취소 여부가 그대로 실린다.
3. **`EndAbility` 가 어빌리티 자신의 `ScopeLockCount` 로 지연돼도 문제없다.** 지연분은 락이 풀리는 `CallActivateAbility` 안에서 소진된다. 더 늦어지면 그냥 기존 비동기 경로로 처리된다.
4. **브로드캐스트 도중 델리게이트 해제는 안전하다.** 지금도 콜백에서 `CleanUp()` 이 `Remove` 를 부르고 있어 새로 생기는 위험이 아니다.
