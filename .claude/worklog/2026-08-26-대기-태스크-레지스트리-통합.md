# 대기 태스크 레지스트리 인프라 통합

## 계획

### 목표
통보를 기다리며 Running 으로 머무는 두 ST 태스크(`WaitForInteraction`·`WaitSpawnersKilled`)가 대기 등록부를 통째로 복제하고 있고, 로케이터 해석 컨텍스트에서 이미 한 지점이 갈라졌다. 등록/해제/스윕을 공용 템플릿 한 곳으로 뽑고 두 태스크는 조건 판정만 남긴다. 그 참에 해석 기준을 자기 오너로 통일하고 통보를 같은 월드로 좁힌다.

### 수정 범위
| 파일 | 수정할 내용 | 구분 |
|---|---|---|
| `Plugins/WxWorld/.../Private/WxStateTreeWaitRegistry.h` | `TWxStateTreeWaitRegistry<PayloadType>` — Add·Remove·FinishMatching | 신규 |
| `Plugins/WxWorld/.../WxStateTreeTask_WaitForInteraction.cpp` | 익명 namespace 3종 삭제, 해석 컨텍스트를 자기 오너로 교정 | 수정 |
| `Plugins/WxWorld/.../WxStateTreeTask_WaitSpawnersKilled.cpp` | 익명 namespace 3종 삭제, `NotifySpawnerKilled` 가 스포너를 받음 | 수정 |
| `Plugins/WxWorld/.../Public/Spawnable/WxStateTreeTask_WaitSpawnersKilled.h` | `NotifySpawnerKilled` 시그니처 변경 | 수정 |
| `Plugins/WxWorld/.../Private/Spawnable/WxSpawner.cpp` | `NotifySpawnerKilled(this)` 로 호출 | 수정 |

### 접근 방식
- **페이로드 템플릿 + 술어**: 두 태스크가 다른 것은 대기 조건과 그 조건이 보는 데이터뿐이다. 등록부는 페이로드 타입만 템플릿 인자로 받고, 판정은 호출부가 넘긴 술어가 한다.
- **월드는 저장하지 않고 살아 있는 오너에서 뽑는다**: 액터의 월드는 바뀌지 않으므로 필드를 늘릴 이유가 없다.
- **역순 순회 유지**: `FinishTask` → `ExitState` → `Remove` 가 자기 인덱스를 지우므로 아직 안 본 낮은 인덱스는 밀리지 않는다.

### 구현·결정과 그 이유
- **페이로드만 템플릿, 판정은 술어로**: 두 태스크가 다른 것은 대기 조건과 그 조건이 보는 데이터뿐이다. 등록부가 조건까지 떠안으면 대기형 태스크가 늘 때마다 등록부를 고쳐야 한다.
- **월드를 저장하지 않는다**: 리뷰 제안은 「등록 시 오너의 월드를 함께 담기」였으나, 액터의 월드는 바뀌지 않으므로 통보 시점에 살아 있는 오너에서 뽑으면 된다. 필드가 하나 줄고 등록·통보가 어긋날 여지도 없다.
- **역순 순회를 그대로 가져왔다**: `FinishTask` → `ExitState` → `Remove` 가 자기 인덱스를 지우므로, 역순이어야 아직 보지 않은 낮은 인덱스가 밀리지 않는다.
- **람다 1개**: 상호작용 술어만 통보 액터를 캡처해야 해서 코딩 규칙 3 의 「반드시 필요한 경우」로 봤다. 스포너 쪽은 기존 자유 함수 주소를 그대로 넘긴다.
- **해석 컨텍스트는 통보 액터로 되돌렸다**: 계획에선 스포너 쪽과 맞춰 자기 오너로 통일하려 했으나, 엔진 `FActorLocatorFragment::Resolve` 의 1차 경로가 컨텍스트의 `GetTypedOuter<ULevel>()` 로 스트리밍 월드를 찾아 푸는 것이라, GameState(PersistentLevel)를 컨텍스트로 주면 이 경로를 못 탄다. 여기서 실패해도 경로 직접 해석(`Path.ResolveObject()`, 에디터·PIE 는 컨텍스트 패키지의 인스턴스 픽스업 포함) 폴백이 남으므로 곧바로 해석 실패는 아니다. 다만 WP 런타임 셀의 액터는 런타임 경로·아우터가 저작 시점과 달라질 수 있어 그 폴백으로 잡힌다는 보장이 없다 — 확정적 실패가 아니라 보장 없음이고, 그 정도로도 통보 액터 컨텍스트를 택할 근거는 된다. 리뷰가 통보 액터 컨텍스트를 문제 삼은 근거(남의 월드 통보로도 해석 성립)는 월드 좁히기가 직접 막고, 매칭이 항등 비교라 오탐도 없다.
- **`NotifySpawnerKilled` 가 스포너를 받는다**: 월드를 알아야 통보를 좁힐 수 있다. `NotifyInteracted` 는 이미 액터를 받으므로 그대로다.

### 계획 대비 달라진 점
- **해석 컨텍스트 통일을 철회했다.** 위 사유 참조 — 통일이 주는 것은 일관성뿐인데, 정적으로 확증할 수 없는 WP 해석 실패 위험을 감수해야 했다. 리뷰가 지적한 실제 결함(크로스 월드 완료)은 월드 좁히기로 이미 닫혔다.

### 후속 점검과 보강

구현 직후 사이드이펙트를 되짚어 두 가지를 고쳤다.

- **`FinishMatching` 이 항목을 참조가 아니라 값으로 잡는다.** 기존엔 `const FWait&` 를 잡은 뒤 술어 → `FinishTask` 순으로 썼는데, 술어 실행 중 `Add` 가 일어나면 배열 재할당으로 그 참조가 매달린다. 현재 경로로는 닿지 않는다 — `SyncFind` 는 Find 전용이라 로드·스폰을 유발하지 않고(`SyncLoad` 와 구분된다), `FinishTask` 는 완료 상태만 세워 동기 `EnterState` 재진입이 없다. 리팩터로 새로 생긴 결함이 아니라 두 cpp 에 흩어져 있던 같은 모양인데, 한 곳으로 모인 김에 복사 한 줄로 닫았다.
- **`AreAllSpawnersKilled` 를 태스크의 private static 멤버로 옮겼다.** `.cpp` 익명 namespace 의 자유 함수라 「내부 헬퍼는 익명 namespace 대신 호출부에 인라인」과 어긋났는데, 호출부가 둘(진입 1회 평가 + 통보 술어)이라 인라인하면 해석 루프가 복제된다. 멤버로 올리면 자유 함수가 사라지면서 정의는 한 벌로 남는다. 판정 로직 자체는 두 호출부 모두 필요하다 — 통보 쪽은 한 마리 처치가 전원 처치가 아니라서, 진입 쪽은 `bNeverRevive` 스포너가 이미 처치인 채로 복원되면(트리거의 `Respawn` 이 조기 반환한다) 다시는 `MarkKilled` 가 오지 않아 스텝이 영구히 멈추기 때문이다. 익명 namespace 는 레지스트리 객체만 남아 `WaitForInteraction.cpp` 와 같은 모양이 됐다.
- **진입 시 전부 미해석이면 경고를 남긴다.** `AreAllSpawnersKilled` 는 미해석에 조용히 `false` 를 답하므로, 해석이 깨지면 「스텝이 안 넘어간다」는 증상만 남고 원인이 안 보였다. 판정 함수 안이 아니라 `EnterState` 에 둔 것은 노이즈 때문이다 — 통보 술어는 처치가 일어날 때마다 돌고, 대기 대상 셀이 언로드된 동안 다른 곳에서 적이 죽으면 전부 미해석이 정상적으로 성립해 경고가 늑대소년이 된다. 진입 1회면 스팸이 없고 나중에 로그로 원인을 짚기에 충분하다. 문구는 형제 태스크 `TriggerSpawnersByLocator` 의 「해석된 스포너가 없음」과 결을 맞췄다.
- **역순 순회의 근거 주석을 정정했다.** 「완료한 노드가 ExitState 에서 자기 등록을 걷어가므로」는 사실이 아니다. `FStateTreeWeakExecutionContext::FinishTask` 는 `MakeStrongExecutionContext().FinishTask()` 로 완료 상태만 기록하고, 전이·ExitState 는 트리가 다음에 전이를 평가할 때 일어난다. 스윕 도중 실제로 `Remove` 가 오는 경로는 오너 사망 정리뿐이며, 역순이 옳은 이유도 그쪽이다. 이 문구 역시 기존 두 cpp 에서 그대로 옮겨온 것이다.

부수적으로 확인한 사실:

- **월드 좁히기가 정상 완료를 막지 않는 것은 정적으로 닫힌다.** 두 태스크를 쓰는 에셋은 `ST_QuestStep_InteractTarget`·`ST_QuestStep_KillEnemies` 둘뿐이고 참조자는 `ST_Quest_Main1` 하나 — 전부 퀘스트 ST 다. 퀘스트 러너는 `UWxQuestComponent::BeginPlay` 가 `HasAuthority()` 일 때만 만들므로 클라 월드엔 등록 자체가 없고, 통보 두 경로도 권위 게이트다(`UWxAbility_Interact` 는 ServerOnly + `HasAuthority` 이중, `MarkKilled` 는 조기 반환).
- **`GetOwner()` 는 ST 컴포넌트의 소유 액터다**(엔진이 `FStateTreeExecutionContext(*GetOwner(), ...)` 로 넘긴다). 퀘스트는 GameState, 장치는 AWxDevice 라 `GetWorld()` 가 언제나 유효하다.
- **에디터·쿠킹 빌드의 UOL 해석 차이는 실질적으로 없다.** `FActorLocatorFragment::Resolve` 에서 `#if WITH_EDITORONLY_DATA` 로 갈리는 것은 마지막 폴백 한 줄뿐이고, 에디터 쪽에 더 붙은 PIE 인스턴스 픽스업과 리다이렉터 재시도(`PreSavePath` → `GRedirectCollector`, 이것도 `WITH_EDITOR` 전용)는 에디터에만 있는 왜곡을 되돌리는 보정이다. 저장·쿡되면 경로가 확정되므로 양쪽이 같은 조회를 한다. 정작 문제가 되는 WP 셀 해석 경로(`GetLevelFromContext` → `ResolveActorWithinLevel`)는 `#if` 밖이라 환경에 의존하지 않는다 — 즉 PIE 실측으로 유효하게 검증된다.
- **Private 루트 헤더를 서브디렉터리 cpp 에서 경로 없이 include 하는 것은 성립한다** — UBT 가 모듈의 `Private` 를 PrivateIncludePaths 에 자동 추가한다(`UEBuildModuleCPP.cs`). 프로젝트에 선례가 없던 형태라 확인했다.
- **`WaitSpawnersKilled::EnterState` 의 조기 `Succeeded` 경로는 `Add` 를 건너뛰어 `WaitHandle` 이 직전 진입 값으로 남는다.** 이어지는 `ExitState` 가 그 값으로 `Remove` 를 부르지만 핸들을 재사용하지 않으므로 이미 없는 번호라 무동작이다. 즉 「재사용하지 않는다」가 이 안전성의 전제이니, 나중에 핸들 압축·재사용을 넣으면 그 자리에서 깨진다.

### 후속 과제
- PIE 실측은 여전히 하지 않았다. 다만 위 정적 확인으로 현재 조립에서 월드 좁히기가 정상 완료를 막을 여지는 없다.
- 이 태스크를 장치 ST(클라에도 붙는다)에서 쓰기 시작하면 그때 동작이 갈린다 — 클라 노드는 더 이상 완료되지 않고 StateTag 추종 수렴으로만 빠져나온다. 패키지 빌드와 일치하는 올바른 방향이지만, PIE 에서 보이던 「클라도 같은 프레임에 자연 전이」 그림은 사라진다.
- 두 태스크의 해석 컨텍스트가 여전히 다르다(통보 액터 / 자기 오너). 상황이 달라서 갈라진 것이지만, `WaitSpawnersKilled` 가 WP 셀의 스포너를 GameState 컨텍스트로 제대로 해석하는지는 확인하지 않았다 — 이번 변경 이전부터 그랬던 코드다. 실측 때는 같은 스텝의 `TriggerSpawnersByLocator` 가 카나리아다: 완전히 같은 컨텍스트·같은 `SyncFind` 를 쓰므로, 해석이 안 되는 조립이면 적이 아예 스폰되지 않아 즉시 드러난다.
- `FinishMatching` 에 재진입 보호는 없다. 술어나 완료가 같은 등록부에 `FinishMatching` 을 다시 부르면 바깥 루프의 인덱스가 어긋난다 — 현재 경로에선 발생하지 않는다.
- 레지스트리 헤더의 `#include "Engine/World.h"` 는 불필요하다(포인터 비교뿐이라 전방선언으로 충분).
