# 영역별 상호작용 프롬프트

## 계획

### 목표
엘리베이터처럼 상호작용 영역이 여럿인 기믹이 영역마다 다른 HUD 프롬프트를 띄우게 한다. 지금은 프롬프트가 액터 단위 pull 이라 플랫폼·콜콘솔 A·콜콘솔 B 중 무엇을 조준해도 같은 텍스트가 나온다. 텍스트는 C++ 이 아니라 BP 디폴트(영역별 고정)와 ST 에셋(상태별 override) 두 층에서 author 한다.

### 접근 방식
- **프롬프트 pull 에 Source 를 실어 보낸다**: 스캐너·PC 는 어느 메시가 후보/선택인지 이미 알면서도 대상에게 알려주지 않아 영역을 가를 수단이 없었다. 응답·자격 판정이 이미 Source 로 영역을 가르므로 프롬프트만 그 관례에서 빠져 있던 비대칭을 없앤다.
- **텍스트 저작은 2층**: 콘솔 이름처럼 상태와 무관한 고정 텍스트는 BP 디테일 패널의 영역별 명명 필드에 두어 한 곳에서 다 채우고, 상태에 따라 문구가 달라져야 하는 영역만 ST 의 `Wx Enable Interaction` Prompt 로 덮는다. 조회 순서는 ST 세팅값 → BP 영역별 필드 → 기믹 기본값.
- **명명 필드 선택**: 컴포넌트가 명명 필드인 것과 같은 결이라 어느 필드가 어느 영역인지 헷갈릴 여지가 없고, 응답 분기와 같은 구조라 읽는 사람이 두 곳을 나란히 볼 수 있다.
- **ST 저장은 메시 키 맵**: 한 상태가 여러 영역을 켜면 마지막 노드가 이기던 문제를 없앤다. 여전히 로컬 전용(비복제)이며 근거는 종전과 같다 — ST 가 각 피어에서 실행되어 로컬로 채우고 스캐너도 로컬에서 pull 한다.

### 구현·결정과 그 이유
- **우선순위는 베이스가 소유하고 자식은 폴백만 override**(계획에서 변경): 처음엔 자식이 `GetInteractionPrompt` 를 직접 override 하는 그림이었으나, 그러면 "ST 값이 먼저"라는 규칙을 자식마다 다시 써야 하고 한 자식이 빠뜨리면 조용히 ST 층이 무시된다. 베이스가 순서를 정하고 자식은 폴백 훅만 채우게 나눴다.
- **문구 저작은 BP 디폴트가 1층, ST 가 2층**(사용자 요구): 콘솔 이름처럼 상태와 무관한 문구를 상태 수만큼 반복 입력하지 않도록, 영역별 고정 문구는 BP 디테일 패널 한 곳에 두고 상태에 따라 달라지는 영역만 ST 에서 덮는다.
- **영역별 명명 필드**: 컴포넌트가 명명 필드인 것과 같은 결이고, 응답 분기와 구조가 같아 두 곳을 나란히 읽을 수 있다.
- **끄는 상태에서 엔트리 제거**: 표시엔 영향이 없지만(비활성 메시는 스캔에 안 잡힘) 다시 켤 때 이전 상태의 문구를 물려받지 않는다.
- **맵 조회의 const 벗기기**: `Source` 는 읽기 전용 계약인데 TMap 키는 비const 포인터라 조회용으로만 `const_cast` 한다. 맵을 통해 대상을 수정하지 않는다.

### 계획 대비 달라진 점
- 자식이 `GetInteractionPrompt` 를 override 하는 대신 베이스에 폴백 훅 `GetDefaultInteractionPrompt` 를 신설했다(위 참조).

- **에셋 author 미완 (사용자, 에디터)**: `BP_Elevator` 의 프롬프트 필드 3개 입력. 층별로 플랫폼 문구를 바꾸려면 `ST_Elevator` 의 해당 상태 `Wx Enable Interaction` Prompt 를 채운다.
