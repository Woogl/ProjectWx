# 몽타주 선택기를 걷고 어빌리티가 몽타주를 직접 정의

## 계획

### 목표
`FWxMontageSelector`의 태그 기반 세트 선택이 실사용 가치를 잃었다 — 공중 공격·회피 반격이 별도 어빌리티 BP로 갈라지면서 아바타 태그 조건은 실사용 0건이 됐고, 세트가 여럿인 피격 반응·처형은 세트마다 몽타주 1개라 같은 태그 분기가 데이터와 코드에 두 벌 존재한다. 선택기를 지우고 파생 어빌리티가 각자 필요한 몽타주를 직접 정의하게 되돌린다.

### 접근 방식
- **공격·스킬은 콤보 배열 하나**: 세트 개념을 없애고 어빌리티가 배열과 진행 인덱스를 직접 갖는다. 전진·되감기 규칙은 선택기가 하던 그대로이며, 되돌림 지점도 캔슬 종료와 완주 두 곳으로 같다. 두 클래스에 같은 두 줄이 나란히 놓이지만 공통 부모 신설은 BP 부모 교체를 부르므로 하지 않는다.
- **피격 반응은 이전 7필드 복원**: 폴백 겸 일반 피격 하나와 종류별 여섯. 태그→몽타주 매핑만 private 함수로 모으고, 부수 효과 분기(그로기 강등·넉업 띄우기·가해자 응시)는 갈래 모양이 달라 그대로 둔다.
- **처형은 삼항 한 줄**: 이미 계산해 둔 변형 판정이 짝 피격 태그와 함께 몽타주까지 고른다.
- **에셋은 값을 떠 두고 이관**: 프로퍼티 경로가 바뀌어 리다이렉트로 못 살린다. 코드에 손대기 전 10개 GA의 값을 읽어 두고, 빌드·에디터 재시작 뒤 새 경로에 되쓴다.
- **잃는 것**: 아바타 태그로 몽타주를 가르는 데이터 축(실사용 0건)과, 새 피격 종류를 데이터만으로 추가하는 경로. 후자는 종류마다 부수 효과가 코드에 있어 애초에 데이터만으로 끝난 적이 없다. 2026-08-15의 "가드를 선택기로 전환한다"는 후속 계획도 대상이 사라져 폐기한다.

### 구현·결정과 그 이유
- **선택기를 지운 근거는 데이터였다**: 에디터에서 10개 GA를 직접 읽어보니 아바타 태그 조건은 한 건도 쓰이지 않았고, 세트가 여럿인 두 어빌리티도 세트마다 몽타주가 하나뿐이었다. 공중 공격·회피 반격이 별도 어빌리티로 갈라진 뒤로 "한 어빌리티 안에서 태그로 갈래를 만드는" 축 자체가 쓰이지 않게 됐다.
- **공격·스킬의 중복은 감수**: 전진·되감기가 두 줄이라 공통 부모를 새로 세우는 비용(BP 부모 교체)이 중복보다 크다. 08-11·08-15에 두 번 "별건"으로 미뤄둔 판단을 유지한다.
- **피격 반응은 두 갈래를 합치지 않았다**: 부수 효과 쪽은 다섯 종류가 가해자 응시라는 한 갈래를 공유해, 몽타주 선택과 한 체인으로 접으면 같은 호출이 다섯 번 흩어진다. 선택만 함수로 떼고 폴백은 마지막 한 줄이 맡는다 — 종류별 필드를 비워두면 자동으로 일반 피격으로 떨어져 선택기 시절 계약이 유지된다.
- **처형은 함수가 필요 없었다**: 변형 판정이 이미 짝 피격 태그를 고르고 있어 몽타주도 같은 삼항 한 줄로 붙는다.
- **에셋은 값을 먼저 떠 두고 이관**: 프로퍼티 경로가 바뀌어 리다이렉트로 못 살린다. 코드 수정 전에 값을 읽어 두고, 빌드·에디터 재시작 뒤 새 경로에 되쓰고 컴파일·저장한 다음 10개 전부 다시 읽어 대조했다.

### 계획 대비 달라진 점
- 배열 기입이 크기 변경과 값 변경을 한 번에 받아, 예상했던 2단계(비우고 다시 채우기)가 필요 없었다.

### 후속 과제
- **PIE 미검증**: 컴파일과 에셋 데이터(저장 후 재조회, 10개 전부 일치)까지 확인했다. 약공격 4단 진행·터미널 되감기·피격 캔슬 후 1단 재시작, 강공격·공중 공격·회피 반격, 스킬 3의 3단 진행, 피격 종류별 몽타주와 처형·백스탭 짝 피격 프레임 싱크는 직접 플레이로 확인이 필요하다.
- **공격·스킬 통합**: 두 클래스의 차이가 여전히 생성자 태그와 끊고 들어가는 발동 분기뿐이다. BP 부모 교체가 따라오므로 별건으로 남긴다.
