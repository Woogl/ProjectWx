# HitReact 태그를 컨텍스트 대신 스펙에서 직접 읽기

## 계획

### 목표
`FWxDamageInfo::MakeSpecs`가 이미 `Event.HitReact.*`를 스펙의 DynamicAssetTags에 싣는데, ExecCalc가 그걸 다시 꺼내 EffectContext에 복사하고 소비 지점이 컨텍스트에서 읽고 있다. 소비 지점이 스펙에서 바로 읽게 해 중간 복사를 없앤다.

### 수정 범위
| 파일 | 수정할 내용 | 구분 |
|---|---|---|
| `Plugins/WxCombat/.../Damage/WxCombatEffectContext.h/.cpp` | `HitReactTag` 필드·getter 삭제, `SetDamaged` 인자 3→2개, `ClearDamageResult`·`NetSerialize`에서 제거 | 수정 |
| `Plugins/WxCombat/.../Effect/WxEffect_Damage.cpp` | 태그 Filter 블록 삭제 | 수정 |
| `Plugins/WxCombat/.../Effect/WxEffect_Burn.cpp` | `SetDamaged` 호출 인자 정리 | 수정 |
| `Plugins/WxCombat/.../Attribute/WxCombatAttributeSet.cpp` | `PublishDamageResult`가 DynamicAssetTags에서 직접 취득 | 수정 |

### 접근 방식
- **입력 데이터와 계산 결과를 갈라 담는다**: HitReact 태그는 공격이 스펙에 실어 보낸 입력이라 소비 지점이 스펙에서 그대로 읽으면 된다. 크리 여부는 ExecCalc가 계산해 만든 값이라 스펙 태그로는 나를 수 없어 컨텍스트에 남긴다(태그 캡처는 스펙 생성 시점에 끝나고 ExecCalc에서 스펙은 const다).
- 같은 함수가 이미 `Damage.Unblockable`을 같은 컨테이너에서 읽고 있어 취득 경로가 하나로 모인다.

### 구현·결정과 그 이유
- **크리 여부는 옮기지 않았다**: 태그 캡처는 스펙 생성 시점에 끝나고 ExecCalc에서 스펙은 const라, 그 안에서 계산한 값은 스펙 태그로 나를 방법이 없다. Lyra가 `CapturedSourceTags`를 쓰는 것은 공격자의 당시 상태를 메시지에 싣는 용도이지 계산 결과 통로가 아니다.
- **취득 경로가 하나로 모였다**: 같은 함수가 바로 옆에서 `Damage.Unblockable`을 같은 컨테이너에서 읽고 있었다. 반응 태그만 컨텍스트를 경유할 이유가 없다.

### 계획 대비 달라진 점
계획대로.

### 후속 과제
- 컨텍스트에 남은 `DamageResult`·`FinalDamage`는 화상 플로터(주기형 훅)만 쓴다. 그 훅까지 어트리뷰트 훅에 합치면 컨텍스트는 크리 여부 하나로 줄어든다.
