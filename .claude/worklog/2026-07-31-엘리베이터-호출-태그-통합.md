# 엘리베이터 호출 콘솔 태그를 StateTree.Interact 로 통합

## 계획

### 목표

엘리베이터 호출 콘솔 A/B 를 가르려고 프로젝트 전역 태그 두 개(`StateTree.Interact.Elevator.CallA`/`CallB`)를 두고 있다. 특정 기믹의 버튼 하나를 `WxCore` 의 태그 어휘집에 올린 셈이라, 다중 영역 기믹이 늘 때마다 공용 계약만 담아야 할 모듈이 부푼다. 구분을 태그가 아니라 이벤트 페이로드의 `Source`(눌린 영역 메시) 비교로 옮겨 두 태그를 없앤다.

### 접근 방식

- **구분 축을 태그에서 컴포넌트로 옮긴다**: 눌린 영역은 이미 이벤트 페이로드로 전 피어에 실려 온다. 전이가 그 값을 대상 메시와 비교하면 태그를 새로 만들지 않고도 갈린다. 헤더 주석과 콘솔 메시의 `AllowPrivateAccess` 노출이 원래 이 방식을 전제로 쓰여 있었으므로, 코드와 에셋이 다시 일치하게 된다.

- **조건은 꼭 필요한 상태에만 둔다**: 조사해보니 AtStart/AtEnd 는 자기 층 콘솔을 꺼두어 남은 영역이 모두 같은 목적지라 이미 공용 태그 단일 전이였다. 두 콘솔이 서로 다른 끝점을 부르는 Closed 만 조건이 필요하다.

- **양쪽 전이에 모두 조건을 단다**: 한쪽만 달고 다른 쪽을 무조건 전이로 두어도 첫 매치 우선 규칙으로 동작하지만, 행 순서에 암묵적으로 기대게 된다. 전이를 추가하다 순서가 바뀌면 조용히 깨지므로 둘 다 명시한다.

### 구현·결정과 그 이유

- **에셋 저작은 에디터에서 했다**: 조건의 두 입력은 리터럴이 아니라 바인딩이어야 한다(비교 대상이 인스턴스 액터의 컴포넌트라 에셋 시점에 존재하지 않는다). 바인딩 저장소가 편집 가능한 프로퍼티로 노출되지 않아 MCP 기입 경로가 없었고, 콘솔 태스크의 기존 메시 바인딩까지 건드릴 위험이 있어 프로퍼티 직접 쓰기도 피했다.

- **순서 의존 대신 양쪽 명시**: 위 계획대로. 한쪽 조건 + 무조건 폴백이 더 짧지만, 깨졌을 때 증상이 "무반응"이 아니라 "엉뚱한 층으로 감"이라 늦게 발견된다.

- **바인딩 누락을 문서의 함정 목록에 넣었다**: 미바인딩이면 두 비교 대상이 모두 null 이라 조건이 항상 참이 되고 위 전이가 언제나 이긴다. 코드가 잡을 수 없고 컴파일도 통과하므로 문서에 남겼다.

- **검증**: WxEditor 빌드 성공. PIE 에서 Closed 의 CallConsoleB 가 Location B 로 가는 것까지 확인했다(바인딩 정상).

### 계획 대비 달라진 점

- **콘솔 태스크의 `InteractEvent` 를 비우는 대신 `StateTree.Interact` 를 명시했다**: 비워도 코드가 같은 태그로 폴백하므로 동작은 같다. 명시 쪽이 그 영역이 무엇을 발행하는지 패널에서 바로 읽혀 그대로 두었다.

### 후속 과제

- **`InteractEvent` 필드가 전 프로젝트에서 미사용이 되었다**: 지금은 어떤 에셋도 공용 태그 외의 값을 쓰지 않는다. 태그 계층으로 신호를 갈라야 할 일이 끝내 없다면 필드와 `OnInteracted` 의 조회 분기를 걷어내는 것을 검토한다.
