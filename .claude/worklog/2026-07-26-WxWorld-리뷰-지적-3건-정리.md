### 접근 방식

- **발견 8**: 바로 아래 상호작용 불가 게이트가 이미 `UpdateInRange({})` 로 정리하므로 두 조기 리턴 경로의 동작을 일치시키기만 한다. `UpdateInRange` 는 약참조 메시와 컴포넌트 메서드만 만져 월드 없이도 안전하다.

- **발견 9**: `WxCombat` 의 배치를 그대로 따른다(모듈 헤더에 선언, 모듈 cpp 에 정의). 다른 도메인 모듈이 전부 같은 형태라 새 규약이 아니다.

- **발견 10**: 아키타입 조회는 outer 아키타입 재귀 + 이름 검색이라 상수 시간이 아닌데 `Tick` 이 매 프레임, 움직이는 컴포넌트마다 반복한다(엘리베이터면 문 2장 + 플랫폼 동시). 이미 `MoveSpeed` 를 `EnterState` 에서 1회 산출해 인스턴스 데이터에 캐시하는 구조라, 목표 위치를 같은 자리에 나란히 넣고 `Tick` 은 읽기만 한다. `GetMoveAnchor` 는 호출부가 `EnterState` 하나만 남지만 앵커 개념을 설명하는 이름·주석이라 그대로 둔다. `ComponentSplineMove` 는 이 헬퍼를 쓰지 않아 영향이 없다.

### 구현·결정과 그 이유
- **목표 위치 캐시 지점을 `EnterState` 첫머리로**: 즉시 스냅 분기와 라이브 전이 분기가 둘 다 목표를 쓰므로, 분기 이전에 한 번 채워 두 경로가 같은 값을 참조하게 했다. `MoveSpeed` 산출식도 이 캐시를 쓰도록 바꿔 같은 값에서 속도가 나온다.
- **`Tick` 은 캐시를 const 참조로만 읽음**: 목표는 아키타입 오서링 데이터에서 오므로 상태 활성 중 변할 이유가 없다. 기존 코드도 `MoveSpeed` 를 1회 산출해 재사용하고 있었으니 같은 전제다.
- **`GetMoveAnchor` 존치**: 호출부가 `EnterState` 하나만 남았지만 앵커 개념을 설명하는 이름·주석이라 그대로 뒀다. 같은 익명 네임스페이스의 다른 헬퍼들과 짝을 이룬다.
- **로그 카테고리는 `WxCombat` 배치를 그대로 복제**: 다른 도메인 모듈 5개가 전부 같은 형태라 새 규약을 만들지 않았다.
