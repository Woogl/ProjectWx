# 배타 액션 규칙을 WxAbilityBase 한 호출로 통합하고 태그를 Trait.Ability.Exclusive로 개명

## 계획

### 목표

`Trait.Exclusive` 마커와 차단이 14개 어빌리티 생성자에 복제돼 있어 어떤 어빌리티가 배타 액션인지 한눈에 안 보인다. `UWxAbilityBase::SetExclusive()` 한 호출로 선언하게 한다. 부르지 않으면 배타가 아니므로 새 어빌리티가 모르는 새 배타가 되지 않고, 배타 액션 전원이 그 이름으로 잡힌다.

### 수정 범위
| 파일 | 수정할 내용 | 구분 |
|---|---|---|
| `.../Ability/WxAbilityBase.h/.cpp` | `SetExclusive()` 추가 | 수정 |
| Attack · Dodge · Guard · Skill · Ultimate · Pattern (WxCombat) | 마커·차단 두 줄 → `SetExclusive()` 한 줄 | 수정 |
| Interact · UseItem (WxGame) | 동일 | 수정 |

### 접근 방식

- **생성자에서 즉시 적용**: 초기화 단계를 하나로 유지한다. 값을 읽는 플래그였다면 베이스 생성자가 서브클래스보다 먼저 도는 탓에 `PostInitProperties` 같은 두 번째 단계가 필요했다.
- **예외 6종은 손대지 않는다**: 반응형 4종(Death·Groggy·Finisher·HitReact)은 막되 막히면 안 되고, Sprint 는 막히되 막으면 안 된다. LockOn 은 양쪽 다 아니다. 부르지 않는 것이 기본이라 이들은 현행 코드가 그대로 정답이다.
- **`CancelAbilitiesWithTag` 는 건드리지 않는다**: 취소는 차단과 다른 축이고 어빌리티마다 의도가 갈린다.
- **주석 이관**: 앵커를 잃는 지식 두 가지(차단에는 self-exception 이 없어 자기 재발동까지 막힌다 — 가드가 페이즈를 유지하는 방식 / 애셋 태그를 편집한 BP 는 컨테이너를 통째로 가져 베이스 마커가 반영되지 않는다)를 베이스 주석으로 옮긴다.

## 완료

### 수정한 파일
| 파일 | 수정한 내용 | 구분 |
|---|---|---|
| `.../Ability/WxAbilityBase.h/.cpp` | `SetExclusive()` 추가 | 수정 |
| Attack · Dodge · Guard · Skill · Ultimate · Pattern (WxCombat) | 마커·차단 두 줄을 `SetExclusive()` 한 줄로 대체 | 수정 |
| Interact · UseItem (WxGame) | 동일 | 수정 |

### 구현·결정과 그 이유

- **`DynamicAbilityTags` 를 쓰지 않았다**: 엔진이 차단·취소 판정에서 애셋 태그만 보고 이 컨테이너는 GE 소스 태그로만 읽는다. 옮겼다면 배타 규칙 전체가 조용히 죽었다.
- **플래그가 아니라 호출인 이유**: 베이스 생성자는 서브클래스가 값을 정하기 전에 돈다. 값으로 두면 읽을 시점이 생성자 밖(`PostInitProperties`)으로 밀려 초기화가 두 단계가 되고, BP CDO 는 직렬화가 그 뒤에 와서 어긋날 여지도 남는다. 호출은 그 자리에서 끝난다.
- **인자를 받지 않는다**: 애셋 태그를 인자로 받으면 `SetAssetTags` 자리를 대신하게 돼 태그를 세팅한다는 사실이 이름에 묻히고, 자기 태그가 없는 Pattern·Skill 은 빈 컨테이너를 넘겨야 한다. 대신 `SetAssetTags` 뒤에 불러야 한다는 순서 조건이 생기는데, 어기면 형제들과 달리 마커만 빠져 테스트에서 곧바로 드러나므로 주석으로 못 박았다.
- **예외 6종을 그대로 둔 이유**: 반응형 4종은 마커가 붙으면 활성인 공격의 차단에 걸려 피격 반응·사망이 발동을 못 한다. 스프린트는 마커를 떼면 취소 그물에서도 빠져 아이템 사용·사망이 달리기를 못 끊는다. 락온은 양쪽 다 아니다.
- **가드의 self-block 설명을 베이스로 옮겼다**: 코드 줄이 사라지면서 앵커를 잃는 지식이라, 차단에 self-exception 이 없다는 사실과 그것이 가드의 페이즈 유지 수단이라는 점을 함수 주석에 담았다. BP 가 애셋 태그를 편집하면 베이스 마커가 닿지 않는다는 함정도 같은 이유로 옮겼다.

### 검증

- 새 코드로 띄운 에디터에서 어빌리티 BP CDO 15종의 애셋 태그·차단 목록을 읽어 의도한 표와 정확히 일치함을 확인했다. 배타 9종은 자기 태그 + 마커 + 차단, 스프린트는 마커만, 반응형 4종은 차단만, 락온은 둘 다 없음.
- 애셋 태그를 읽는 다른 코드 네 곳(AI BT 태스크·어빌리티 뷰모델·상호작용 스캐너·공격의 캔슬 대상 조회)은 모두 특정 태그 포함 여부만 보므로 컨테이너 구성이 같은 이상 영향이 없다.
- 에셋 재저장 불필요: 차단 목록을 오버라이드한 BP 는 없고, 애셋 태그를 오버라이드한 BP 는 저장된 컨테이너에 이미 마커가 들어 있다.

### 계획 대비 달라진 점

- 처음엔 `bUseExclusive` 플래그 + `PostInitProperties` 로 구현했으나, 초기화 단계를 하나로 유지하자는 판단에 따라 생성자 호출로 바꿨다.

### 태그 개명

같은 작업의 후속으로 `Trait.Exclusive` 를 `Trait.Ability.Exclusive` 로 바꿨다. C++ 참조를 모두 옮긴 뒤, 애셋에 문자열이 박힌 12종(GA_Attack_*, GA_Pattern_*, GA_Skill_*)은 임시 리다이렉트 ini 를 깔고 리세이브 커맨드릿으로 옮긴 다음 ini 를 지웠다. 리다이렉트 없이 띄운 에디터에서 CDO 를 다시 읽어 새 이름으로 붙어 있음을 확인했다.

리세이브를 폴더 단위로 돌린 탓에 태그와 무관한 같은 폴더 애셋 35종도 함께 재저장돼 변경으로 잡힌다. 다음에는 대상 패키지만 지정하는 편이 낫다.
