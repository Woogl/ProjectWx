# 📋 시스템 기획서 검토 결과

## 🏗️ 던전 배치물 기획서 (Object_Design.md)

> 피드백 내용을 참고하시어 기획서 최신화 부탁드립니다.  
> 항목이 많으니, 구현 우선순위를 상/중/하로 구분해 주시기 바랍니다.

### 1. 📦 배치물 타입
배치물(오브젝트)의 타입을 다음 두 가지로 분류하는 것을 제안드립니다.

| 항목 | 스포너블 (Spawnable) | 기믹 (Gimmick) |
| --- | --- | --- |
| 체크포인트 상호작용 시 | 다시 스폰(리젠), 최초 위치로 재배치 | 영향 없음, 상태 유지 |
| 상태 지속성 | 리젠 시 초기화 | 레벨 이동·재접속·월드 파티션 스트리밍 시에도 유지 |
| 월드 배치 방식 | WxSpawner를 통해서만 배치 | BP 클래스를 레벨에 직접 배치 |
| Instance Editable 편집 | 불가 (클래스 디폴트 사용) | 가능 |
| 예시 | 졸병, 보스, 장식물(Prop) | 문, 엘리베이터 |

### 1-1. 🔄 스포너블 (Spawnable)
플레이어가 체크포인트(화톳불)와 상호작용하면 다시 스폰(리젠)되며, 위치도 최초 배치 위치로 재설정됩니다.  
리젠이 불필요한 대상은 변수를 통해 리젠을 막을 수 있습니다.
- `bShouldRegen`: WxSpawner 인스턴스마다 리젠 가능 여부를 개별 설정하는 변수. 기본값 `true`.
- 리젠 방식: 기존 액터를 파괴한 뒤, 최초 위치에서 다시 생성합니다.

#### 1-1-1. 스포너블의 규칙
- 반드시 WxSpawner를 통해 월드에 배치해야 합니다. 액터 BP 클래스를 직접 배치하면 안 됩니다.
- 스폰되는 액터 클래스의 데이터는 클래스 디폴트를 그대로 사용합니다.
- 스폰되는 액터 클래스의 속성을 Instance Editable하게 편집할 수 없습니다.

#### 1-1-2. 스포너블의 예시
- 졸병: 리젠 가능 (`bShouldRegen == true`)
- 보스: 리젠 불가 (`bShouldRegen == false`)
- 장식물(Prop): 리젠 가능

### 1-2. ⚙️ 기믹 (Gimmick)
- 플레이어가 체크포인트와 상호작용해도 영향을 받지 않습니다. (Persistent & Non-spawnable)
- 레벨 이동, 게임 재접속, 월드 파티션 스트리밍 등의 상황에서도 상태를 유지합니다.

#### 1-2-1. 기믹의 규칙
- BP 클래스를 레벨에 직접 배치합니다. WxSpawner를 통한 스폰은 지원하지 않습니다.
- 인스턴스별로 Instance Editable한 편집이 가능합니다.

#### 1-2-2. 기믹의 예시
- 문: 플레이어 사망 후 부활하더라도 이미 열어 둔 문은 그대로 유지됩니다.
- 엘리베이터: 이동 경로를 Instance Editable하게 편집할 수 있습니다.

### 2. 🎨 아트 리소스 이슈
기획서에 아트 리소스(메시, 시각 효과, 효과음, 애니메이션 등) 관련 내용이 많습니다.  
다만 다수의 아트 리소스를 저나 민석님이 확보하기에는 현실적 어려움이 있고, 우선순위도 낮은 편입니다.  
따라서 민석님께서 판단하시기에 필수적이지 않은 아트 리소스 관련 변수는 항목에서 제거해 주시길 희망합니다.

### 3. 🔍 세부 항목 검토
- 본 문서의 던전 배치물은 모두 **리젠되지 않고 상태가 유지되는 것**으로 보이는데, 앞서 설명한 **기믹**에 포함되는 것으로 이해하면 될까요?
- 적어 주신 모든 설정 항목은 Instance Editable한 변수이고, 구성요소는 Instance Editable하지 않은 방식으로 진행하면 될까요?
- 여러 배치물의 상호작용 범위가 겹쳐 있을 때, 상호작용 UI 표시나 상호작용 결과가 동시에 처리되어도 괜찮을까요?

### 3-1. 🎚️ 레버(공통)
- 레버의 기능이 너무 많고 종류별 차이도 큰데, 굳이 하나의 클래스로 단일화하시는 이유가 있는지 궁금합니다.
- 다른 배치물에 의존적인 레버(엘리베이터, 문 열기 등)가 많은데, 이러한 Controller 성격의 레버는 해당 오브젝트에 포함시키는 편이 낫지 않을지 의견 드려봅니다.

### 3-2. 🎚️ 레버(소환)
- 소환되는 적의 데이터는 어떻게 설정하나요?
- 우리 게임에서 레벨에 배치되는 모든 적은 WxSpawner를 통해 소환될 예정인데, 이 적은 WxSpawner의 제어를 받지 않는 형태를 원하시는 건가요?

### 3-3. 🎚️ 레버(엘리베이터 활성화/호출)
- 엘리베이터 활성화 레버와 호출 레버는 완전히 별개의 레버가 맞나요? 첫 상호작용 시에는 활성화로, 이후부터는 호출용으로 동작하는 방식이 더 자연스러울 수도 있을 것 같아 여쭤봅니다.
- `ElevatorCall 레버는 다른 레버와 달리 한 번 작동해도 영구 비활성화되지 않는다.`라는 문구에 질문이 있습니다. 상호작용이 `1회성 발동`으로 처리된다는 의미가 맞을까요? 만약 그렇다면 소환 레버 역시 1회성 발동인데, `영구 비활성화되지 않음`과 `1회성 발동`의 차이가 무엇인지 함께 질문드립니다.

### 3-4. 🎚️ 레버(퀘스트 웨이브)
- 퀘스트 시스템 선행 구현이 필요하여 보류합니다.
- 본 문서 아래의 "퀘스트 및 웨이브 시스템 관련" 항목에서 자세히 설명하겠습니다.

### 3-5. 🛗 엘리베이터
- 모든 엘리베이터에 레버가 반드시 필요한 것인지, 아니면 레버 없이 단독으로 동작하는 엘리베이터도 있는지 질문드립니다.
- "층수/층간 높이"는 변수로 제공하지 않고, Spline Component의 피벗으로 제공하겠습니다.
- "이동 속도"나 "이동 시간" 변수는 필요하지 않으실까요?
- "전원 없음" 안내는 어떤 방식으로 출력하나요?
- 여러 층 선택 기능은 UI 이슈로 인해 보류하겠습니다. 1층↔2층 간 이동만 지원하겠습니다.
- 조건부 활성화도 보류하겠습니다. 특정 몬스터 처치 후 도달할 수 있는 위치에 ElevatorOn 레버를 배치하는 방식을 권장합니다.

### 3-6. 🚪 문
- 문 잠금과 엘리베이터 활성화는 모두 상호작용을 막기 위한 기능이라 서로 겹칩니다. 모든 상호작용에 대해 활성화/비활성화를 공통 기능으로 두는 편이 낫지 않을까요?

### 3-7. 🔥 체크포인트
- "체크포인트 번호" 변수는 추가하지 않겠습니다. 수동 기입 시 키 중복이 발생할 위험이 있어, 엔진의 GUID로 처리하겠습니다.

### 3-8. 💰 보물상자
- 니즈는 이해했습니다.
- 다만 인벤토리 및 아이템 시스템 선행 구현 작업에 시간이 필요합니다.

### 3-9. ⚡ 전기 문
- 전기가 꺼지면 공격이 발생하지 않을 텐데, 회피할 필요 자체가 없지 않을까요?
- 참고로 현재 전투 기획상 모든 공격은 회피가 가능합니다. 회피 불가능한 공격이 필요하다면 전투 기획자와 추가 논의 바랍니다.
- 우리 게임에서 넉백은 Root motion 애니메이션 재생으로 구현되므로, "넉백 강도" 설정은 맞지 않습니다.
- 접촉 대미지는 단순 고정 대미지를 원하시는 것인지, 아니면 방어력 등의 수치 계산이 포함되어야 하는지 확인 후 전투 기획자와 논의 바랍니다.

## 💀 플레이어 부활 기획서 (Respawn_System.md)

용어에 다소 혼선이 있어, 대상을 기준으로 용어를 재정의하겠습니다.
- 리스폰, 리젠: **적 등의 배치물**이 체크포인트 상호작용 시 다시 생성되는 것
- 플레이어 부활: **플레이어**가 최근 체크포인트에서부터 다시 시작하는 것

Respawn_System.md에 적어 주신 내용을 기반으로 구현이 가능합니다.  
다만 아직 GameSave 관련 작업이 준비되어 있지 않아, 게임 재접속 시점까지 상태가 이어지지는 않습니다.

## 📜 퀘스트 시스템 관련 (Quest_System.md)

시스템 규모가 크고 추가로 고려해야 할 사항이 많아, 일단 보류합니다.

### 1. 💬 피드백
작성해 주신 퀘스트 시스템 기획서는 웨이브에만 국한된 측면이 있습니다.  
퀘스트 시스템은 "조건", "흐름 제어(분기)", "결과" 등을 별도로 만들고(추상화) 이들을 조립하는 구조가 확장성과 활용성 측면에서 좋습니다.  
따라서 이번 기획서는 정식 시스템 기획이라기보다는 "퀘스트의 배치물(액터)화"에 가깝습니다.

### 2. 🩹 임시 대응
신규 시스템 추가 없이, 레벨 배치만으로 대응하는 방향을 희망합니다.
- 임시 방편 1: 구덩이 밑에 다수의 적이 미리 놓여 있게 한다.
- 임시 방편 2: 다수의 적에게 어그로가 끌리는 특정 위치를 반드시 지나가야 진행할 수 있도록 동선을 설계한다.
- 임시 방편 3: 웨이브 발생 지점의 천장에 적을 배치해 두었다가, 특정 볼륨에 닿으면 적이 서 있는 발판을 파괴해 함께 싸우게 만든다.

### 3. 🗓️ 향후 계획
앞으로 민석님께서 이런저런 니즈를 기록해 주시면, 나중에 퀘스트 시스템 구현을 설계할 때 참고하겠습니다.  
정식 퀘스트 시스템은 State Tree ([**참고 문서**](https://dev.epicgames.com/documentation/unreal-engine/overview-of-state-tree-in-unreal-engine?lang=ko)) 기반으로 구상 중입니다.
