# 언리얼 데이터 관리 수단 — 기획자용

> **로직은 프로그래머가 만들고, 값은 기획자가 채운다.**

## 0. 왜 데이터로 빼는가

수치가 코드 안에 박혀 있으면, 하나 바꿀 때마다 프로그래머와 빌드가 필요해서 반복(iteration)이 느리다.

그 수치를 **데이터로 분리**해두면 기획자가 직접, 빌드 없이, 대량으로, 즉시 조정할 수 있다.

이것을 데이터 주도 개발(Data-Driven Development)이라고 부른다.

## 1. 언리얼 엔진의 데이터 컨테이너

데이터는 형식(Type)을 갖춘 값(Value)이다.

언리얼 엔진에서는 데이터 관리를 위해 다음과 같이 다양한 컨테이너를 제공한다.

- **Data Table** — 같은 형식의 항목을 표로
- **Curve Table** — 축을 따라 변하는 곡선 값
- **Data Asset** — 애셋 참조·복합 구조를 담는 낱개 파일
- **블루프린트 변수** — 로직 애셋에 직접 얹은 값
- **Chooser Table** — 조건을 보고 후보 중 하나를 선택

## 2. Data Table — 가장 많이 쓰는 "표"

### 개념

엑셀 같은 표다. **열 = 정해진 항목 형식(스키마), 행 = 개별 데이터**이며, 각 행은 이름(RowName)으로 찾는다.

### 언제 쓰나

**같은 형식의 항목이 많을 때** 쓴다. 캐릭터 스탯, 대미지 계수, 텍스트 현지화 테이블, 상점 목록 등. "엑셀 한 장에 정리할 수 있겠다" 싶으면 Data Table이다.

### 사용법

1. 프로그래머가 먼저 **Row 구조체(열 형식)**를 정의한다.
2. 우클릭 → Miscellaneous → **Data Table** 생성, Row 구조체를 선택한다.
3. 행을 추가하고 RowName을 지정한 뒤 각 칸의 값을 입력한다.
4. 엑셀/구글시트로 관리하다가 **CSV로 저장한 뒤 Data Table에 Reimport**하면 표 전체를 한 번에 갱신할 수 있다.

**예시 — 캐릭터 스탯 테이블** (우리 게임의 `FWxCombatAttributeInitTableRow`)

플레이어·적의 시작 능력치를 한 행에 하나씩 관리한다. 열은 구조체가 정한 스탯 항목이고, 아래 값은 예시다.

| RowName | MaxHP | MaxMP | ATK | DEF | CritRate |
| --- | --- | --- | --- | --- | --- |
| ABS_Player | 1000 | 200 | 50 | 30 | 0.1 |
| ABS_Goblin | 300 | 0 | 20 | 10 | 0.05 |

## 3. Curve Table — 값이 "곡선"일 때

### 개념

Data Table의 형제다. 한 칸에 단일 값이 아니라 **X축에 따라 변하는 곡선**을 담는다.

### 언제 & 사용법

레벨별 경험치, 성장 곡선, 시간에 따른 감소처럼 "단일 값이 아니라 추이"가 필요할 때 쓴다. Curve 애셋 또는 Curve Table을 만들고 **커브 에디터에서 점(키)을 찍어 곡선을 조정**한다. CSV 임포트도 된다.

> 한 칸이 값이면 Data Table, 한 칸이 곡선이면 Curve Table.

## 4. Data Asset — 개성 있는 "낱개 파일"

### 개념

데이터를 담은 **애셋 파일 하나**다. 표의 한 행(Row) 마다 독립된 파일로 저장하는 것이다.

### Data Table과 뭐가 다른가

Data Table 한 칸엔 담기 어려운 것을 담는다. **메시·아이콘·사운드 같은 애셋 참조, 배열, 중첩 구조** 등. 즉 **항목 하나하나가 개성이 강하고 여러 요소를 묶어야 할 때** 쓴다.

> Data Table이 "명단"이라면, Data Asset은 "개인 프로필 카드"다.

### 언제 쓰나

스킬 정의, 캐릭터/적 프리셋, 복잡한 아이템 정의처럼 비주얼·사운드·능력 참조가 얽힌 데이터에 적합하다.

### 사용법

1. 프로그래머가 Data Asset 클래스(필드)를 정의한다.
2. 우클릭 → Miscellaneous → **Data Asset**, 클래스를 선택한다.
3. **디테일 패널**에서 값을 입력하고, 다른 애셋을 드래그해 연결한다.

**예시 — 아이템 정의 데이터 에셋** (우리 게임의 `UWxItemDefinition`)

아이템 하나가 애셋 파일 하나다. 공통 필드(이름·설명·아이콘·카테고리) 위에 **Fragment**(기능 조각)를 배열로 조합해 그 아이템이 무엇을 할 수 있는지 선언한다.

- **DA_Potion_Heal** (Consumable) — Usable(회복 GE) + Charges(충전 3회) + Stackable + Grade(Rare)
- **DA_Sword_01** (Equipment) — Equippable(메시·부착 소켓·장착 효과) + Grade(Epic)

같은 카테고리라도 붙이는 Fragment 조합만 바꿔 세부 행동을 다르게 한다. Data Table 한 칸엔 담기 어려운 애셋 참조·배열·중첩이 자연스럽게 들어간다.

## 5. 블루프린트 변수 — 로직이 포함된 클래스에 함께 위치하는 데이터

### 개념

앞의 셋이 데이터를 **별도 통(표·애셋)**에 담았다면, 이번엔 반대로 **그 기능을 실행하는 BP 자신**에 값을 얹는다. 예를 들어 `GA_Dash`(대시 능력 BP) 안에 "재생할 몽타주, 부여·차단할 게임플레이 태그" 등의 변수가 있고, 그걸 그 BP에서 바로 편집한다.

> BP는 클래스이므로, 멤버 변수와 멤버 함수를 가진다. 이 중에서 멤버 변수에 대한 편집이 바로 이것.
> 프로그래머가 **"노출(Editable)"한 변수만** 기획자가 만질 수 있다.

### Class Defaults — 어디서 바꾸나

BP를 열고 상단 **Class Defaults** 버튼(또는 변수의 기본값 칸)에서 편집한다.

### 언제 BP 기본값 vs 별도 데이터통

- **BP 기본값이 낫다** : 값이 그 능력/액터에 **1:1로 밀착**되고 개수가 적을 때. "궁극기 어빌리티의 UI 아이콘"처럼.
- **Data Table이 낫다** : 여러 유사 항목을 **한 표에서 나란히 밸런싱**하거나 엑셀로 왕복할 때.
- **실무에선 섞어 쓴다** : BP엔 *"어떤 데이터를 쓸지"* 참조를 지정하고, 실제 수치는 Data Table에 두는 식으로 섞어 쓸 수 있다. 예를 들어 능력 BP는 참조할 대미지 행 이름만 가리키고, 대미지 숫자는 대미지 테이블에서 관리하면 밸런싱을 표에서 한 번에 할 수 있다.

## 6. Chooser Table — "저장"이 아니라 "선택"

### 개념

지금까지가 *"데이터를 어디에 담나"*였다면, Chooser는 *"그 중 무엇을 쓸지 상황을 보고 골라주는 규칙 표"*다. if/else 분기를 코드가 아니라 데이터로 옮긴 것이다.

### 언제 & 사용법

상황(입력·컨텍스트)에 따라 **다른 데이터/애셋/애니메이션을 골라야** 할 때 쓴다. Chooser 애셋을 만들고 입력(컨텍스트)을 정의한 뒤, **각 행 = 조건 + 결과**로 채운다. 위에서부터 첫 매칭을 채택한다. 애니메이션을 절차적으로 선택할 때에도 사용한다.

**우리 프로젝트 예시 — BGM Chooser 테이블**

BGM 시스템이 매 상황마다 컨텍스트(플레이어 상태·BGM 분류 태그·활성 소스 태그)를 채워 넘기면, Chooser가 **위에서부터 첫 매칭 행**의 곡(`UWxBGMData`)을 골라준다.

| 순서 | BGM 분류 | 활성 소스 | 결과 곡 |
| --- | --- | --- | --- |
| 1 | 보스 | Enemy.Boss.Dragon | BGM_Boss_Dragon |
| 2 | 전투 (범용) | Enemy.State.Combat | BGM_Combat |
| 3 | 마을 | Player.Town | BGM_Town |
| 4 | 탐험 | — | BGM_Field |

보스전이 시작되면 보스가 소스 태그를 기여해 1~2행이 잡히고, 전투가 풀려 소스가 빠지면 하위 행으로 자동 폴백된다. 곡별 페이드 시간 같은 재생 파라미터는 각 `UWxBGMData` 애셋이 들고 있다.

> 데이터는 Table·Asset에 저장하고, 그 중 무엇을 쓸지는 Chooser가 결정한다.

## 7. 정리 — 언제 뭘 쓰나

### 대표적인 사용 예시

정답이 하나로 딱 떨어지진 않는다. 실무에서 각 수단이 흔히 쓰이는 상황을 예시로 모았다.

- **Data Table** — 무기·방어구 목록, 몬스터 스탯표, 대미지 계수, 상점 판매 목록, 대사/자막 테이블처럼 같은 형식이 줄줄이 반복되는 데이터.
- **Curve Table** — 레벨별 요구 경험치, 시간에 따른 버프 감쇠, 거리별 대미지 감소처럼 값이 축을 따라 변하는 데이터.
- **Data Asset** — 스킬 하나의 정의, 적 캐릭터 프리셋, 무기 스킨 세트처럼 애셋 참조와 여러 요소가 얽힌 개성 강한 데이터.
- **Blueprint Variable** — 특정 능력의 쿨타임·몽타주, 이 문 기믹의 열림 속도처럼 그 BP·액터 하나에만 붙는 소수의 값.
- **Chooser Table** — 상황별 BGM, 절차적 애니메이션 생성처럼 조건을 보고 후보 중 하나를 고르는 경우.

실제로는 한 컨텐츠에 여러 수단이 함께 쓰이는 경우가 많다. 예를 들어 적 캐릭터 하나를 만들 때 — 기본 스탯은 Data Table, 외형·사운드 묶음은 Data Asset, 개별 능력의 쿨타임은 그 능력 BP의 기본값, 전투 BGM은 Chooser로 고르는 식이다.

### 비교표

| 도구 | 한마디 | 우리 게임에서 예시 |
| --- | --- | --- |
| Data Table | 같은 형식 대량 표 | 캐릭터 별 스탯 수치 |
| Curve Table | 값의 곡선 | 레벨업 경험치 (미구현) |
| Data Asset | 개성 강한 낱개 파일 | 아이템 정의 |
| 블루프린트 변수 | 로직 애셋에 직접 얹은 값 | 어빌리티의 아이콘 |
| Chooser Table | 조건으로 선택 | 상황별 BGM |

## 부록 — 다른 데이터 (심화과정)

저장한 데이터는 결국 로딩·저장·설정 계층으로 흘러간다. 기획자가 지금 몰라도 되지만, 이런 것들이 있다는 것만 알아두면 좋다.

- **Config (.ini)** : 프로젝트 전역 설정(프로젝트 이름, 입력, 애셋 규칙 등)을 관리하는 텍스트 파일.
- **Save Game** : 진행도·인벤토리 등 런타임 저장.
- **GameUserSettings** : 해상도·볼륨 등 플레이어 환경 설정.
- **서버 DB** : 유저 계정·진행도 등을 외부 데이터베이스 서버(MySQL·PostgreSQL 등, 캐시엔 Redis)에 저장한다.

> 더 궁금하면 프로그래머에게 물어보면 된다.
