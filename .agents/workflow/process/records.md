# 작업 기록 관리

## 한줄 요약

개별 작업 자료는 tasks에 모으고, 재개·완료 시 유효성과 보존 필요성을 확인합니다.

[Workflow](../index.md) · [Wiki 지식 관리](../../wiki/wiki-maintenance.md)

웹 작업의 상태·판단·확정본과 대화에서 수행한 작업의 미해결 리뷰를 `.agents/workflow/tasks/`에 둡니다. 동일한 질문의 답과 조치 상태는 해당 작업 자료 한 곳에서 관리하고 다른 문서는 연결합니다. 일회성 결과만 있으면 작업 파일을 만들지 않습니다.

## 작업 자료의 보존과 정리

AI는 작업 수행 자체를 장기 기록으로 남기지 않는다. 다음 작업에 필요한 현재 동작·구조적 제약·인간의 중요한 결정과 이유만 기존 Wiki 정본에 통합한다. 코드·설정·Git에서 바로 확인할 변경 나열, 조사 과정, 중간 초안, 해결된 오류, 일회성 빌드 성공은 별도 보고서로 만들지 않는다. 인간의 판단 원문을 AI 요약으로 대체하지 않는다.

작업 자료 파일은 후속 작업에 필요한 유효한 인계, 미해결 사항, 아직 필요한 리뷰·테스트 수용 근거가 있을 때만 유지한다. 생성 전에 같은 대상의 기존 문서를 찾고 그 파일을 갱신한다. 검토일·기준 버전·미검증 범위와 현재 필요한 이유를 본문에 표시하며, 해결된 지적 뒤에 수정 경위를 계속 덧붙이지 않고 현재 결론으로 다시 정리한다. 사용자가 보고서 산출을 명시한 경우에도 중복 생성과 종료 후 보존에는 같은 기준을 적용한다.

### 작업 재개

AI는 관련 작업 자료의 판단·미결정·코드 근거를 현재 원자료와 대조한다. 해결·대체된 내용은 현행 지적에서 제외하고, 영향받은 판단만 이유와 함께 다시 확인한다. 오래된 검토일만으로 결정을 무효화하거나 과거 검증을 현재 버전에 재사용하지 않는다. Workflow 인계는 공용 유효 기록 확인을 먼저 수행한다.

### 작업 완료

인간의 리뷰·테스트 수용 등 해당 작업의 완료 조건을 충족한 뒤 AI가 다음 정리를 수행한다.

1. 재사용할 동작·제약·결정 이유는 기존 Wiki 정본에 통합하고 원자료·판단 근거를 연결한다. 장기 가치가 없는 작업 내용은 옮기지 않는다.
2. 남은 미결정과 예외 수용·승인 근거는 기준 버전과 함께 필요한 최소 범위로 보존한다. 아직 필요한 자료의 위치와 보존 이유를 명시하고, 해결된 지적·중복·임시 자료를 제거한다. 남은 조치나 보존 이유가 없는 리뷰 문서는 유지하지 않는다.
3. 덮어쓰기·삭제로 사라질 인간 판단 원문이나 필요한 과거 근거는 실제 Git 커밋의 파일 내용 또는 별도의 유효한 정본에서 복원할 수 있는지 확인한다. Git 추적 여부만으로 보존됐다고 판단하지 않는다. 미커밋·미추적 자료는 복원 가능성을 확인할 때까지 유지하고 이유를 알린다. 정리는 자동 커밋·푸시 권한이 아니다.
4. 참조하는 Wiki·목차·페이지 메타데이터을 함께 갱신한다. Workflow가 현재 참조하거나 저장 복구 중인 인계 파일은 직접 삭제하지 않는다. 변경 연결과 복구를 확인하고, 확정본·판단 원문은 삭제하지 않는다. 현재 브라우저의 작업·복구 기록을 확인할 수 없으면 해당 자료를 유지한다.
5. 구조·링크 점검 후 정리 결과와 남긴 자료의 이유를 대화로 전달한다. 정리 보고서나 archive 폴더를 추가로 만들지 않는다.

### 정기 점검

정기 점검은 완료·재개 시 정리에서 빠진 중단·방치 작업을 찾는 보조 절차다. 프로젝트 정기 점검 때 중복 대상, 참조가 없는 문서, 완료·폐기 작업의 잔여 자료, 공용 유효 기록과 연결되지 않은 인계, 해결된 지적을 확인한다. 기간 경과나 링크 부재만으로 자동 삭제하지 않는다. 작업 상태를 알 수 없으면 AI가 근거를 조사하고 필요한 완료·폐기 판단만 사람에게 요청한다. 후보와 이유는 대화로 전달하고 실제 정리는 위의 보존·참조 확인 절차를 따른다. 별도 예약 실행이나 자동 삭제 기능을 뜻하지 않는다.

## 작업 기록과 도구

`Docs/Programmer/`는 프로그래머가 직접 관리하는 문서만 둔다. AI는 읽기·인용만 하고 자동 생성·수정·삭제하지 않는다. `.agents/workflow/tasks/`에는 진행 중인 작업 자료와 완료 후에도 필요한 판단·확정·수용 근거를 둔다. 완료 여부는 작업 상태로 관리하며 완료만으로 경로를 옮기지 않는다. 경로 이관은 코드 재검증이나 완료·폐기 판정이 아니며 기존 기준 커밋과 검토일을 유지한다.

tasks의 시점별 검토 자료는 모듈·시스템 정본과 구분한다. 같은 대상을 다시 검토하면 `module_review_<Module>.md`처럼 대상마다 하나인 파일을 갱신하고 날짜를 파일명에 넣어 새 파일을 만들지 않는다. 검토일과 기준 커밋은 본문 머리에 남긴다. 링크 검사는 수행하지만 과거 보고서 자체를 최신 구현으로 표시하지 않는다. 현재 페이지가 보고서를 근거로 인용하면 본문에서 해당 자료와 확인 범위를 연결한다. 보고서에 포함된 주장은 가능한 한 코드·기획 원자료로 재확인한다.

작업마다 worklog를 새로 작성하지 않는다. 파일·코드 변경 내역은 Git 커밋/PR, 현재 구조와 확정된 규칙·필요한 결정 이유·예외·제약은 해당 주제의 정본, 미결정은 관련 검토 결과 문서의 확인할 사항 섹션에 기록한다. 별도 결정 이력 문서는 만들지 않는다. Workflow의 판단 원문·확정본은 기존 보존 절차를 따른다. 모든 작업을 Wiki에 기록할 필요는 없다. Wiki 갱신 이력은 Git에서 확인하며 별도 갱신 로그를 작성하지 않는다.

기존 worklog는 2026-09-20 사용자 요청으로 모두 삭제했다. worklog 폴더를 다시 만들거나 새 기록을 작성하지 않는다.

과거 판단이 필요하면 Git 이력에 남아 있는 자료를 찾아 현재 코드와 대조한다. Git에 보존되지 않은 기록의 복구를 보장하지 않는다. 삭제 전에 전체 기록을 Wiki로 이관하지는 않았다. 과거의 완료·빌드 성공을 현재 버전의 검증 결과로 옮기지 않는다.

`readme-writer`는 호환 이름을 유지하되 knowledge의 해당 주제 페이지를 갱신한다. `module-review`는 후속 조치에 필요한 결과만 `.agents/workflow/tasks/module_review_<Module>.md`에 남긴다. 발견과 보존 이유가 없으면 대화로 전달한다. 리뷰의 제안은 Wiki에 결정으로 자동 반영하지 않는다.
