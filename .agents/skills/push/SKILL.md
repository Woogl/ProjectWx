# 원격 저장소에 커밋 및 푸시

변경 사항을 커밋하고 원격 저장소에 푸시하라.

## 절차

### 1단계: 변경 사항 확인

다음을 병렬로 실행하라:
- `git status` 로 변경/추가/삭제된 파일 목록 확인
- `git diff` 와 `git diff --staged` 로 변경 내용 확인

작업 트리에 변경이 없으면 2~4단계만 건너뛰고 5단계로 간다. 이미 만든 미전송 커밋이나 upstream 없는 새 브랜치가 있을 수 있으므로 여기서 종료하지 않는다.

### 2단계: 변경 분석 및 논리 그룹화

변경된 파일들을 분석하여 **논리적으로 독립된 변경 단위(그룹)** 로 분리하라.

**1차 기준 — 독립성**: 서로 의존하지 않아 따로 되돌릴 수 있고, 별개의 관심사인가? 이것이 그룹을 가르는 핵심 기준이다.

**보조 신호** (1차 기준이 애매할 때만 참고):
- 변경의 성격 (신규 기능, 리팩터링, 버그 수정, 삭제, 문서/설정 등)
- 다루는 시스템·기능 영역 (예: 데미지 계산 / AI BT / UI 위젯 / 빌드 설정)

주의: **하나의 응집된 작업은 여러 영역(C++ + 블루프린트 + UI 등)에 걸쳐도 한 그룹**이다. 영역이 다르다는 이유만으로 쪼개지 마라 — 따로 되돌릴 수 있는 별개 관심사일 때만 분리한다.

**판단**:
- 변경이 하나의 논리 단위로만 묶이면 → 단일 커밋.
- 서로 다른 관심사가 섞여 있으면 → **그룹별로 분리 커밋**한다.
- 한 파일이 여러 그룹에 걸치면, 가장 핵심이 되는 그룹에 통째로 포함시키고 그 사실을 커밋 메시지/보고에 명확히 남겨라. (셸은 비인터랙티브이므로 `git add -p`는 쓸 수 없다. 정 라인 단위 분리가 필요하면 `git diff -- <file> | git apply --cached` 같은 비인터랙티브 패치를 쓰되, 과하면 통째 포함을 택하라.)
- 커밋 순서는 의존 관계를 따른다 — 베이스가 되는 변경(리팩터 등)을 먼저 두어, 가능하면 각 커밋이 단독으로 빌드되도록 정렬하라.

그룹 분리는 **사용자에게 묻지 말고 스스로 판단해 진행**한다 — 그룹을 따로 제시하거나 승인받는 단계는 없다. 분리 결과(각 커밋이 어떤 그룹인지)는 6단계 보고에서 밝힌다.

### 3단계: 커밋 메시지 작성

각 그룹마다 이 프로젝트의 커밋 메시지 컨벤션에 따라 메시지를 작성하라:

```
변경 내용 요약 (한국어)
```

**규칙**:
- 요약은 한국어로 작성
- 하나의 커밋은 하나의 논리 단위만 설명한다. 한 메시지에 "A 및 B 및 C"처럼 무관한 변경을 나열하지 마라(그건 분리 대상이라는 신호다).
- "~를 추가" (신규), "~를 변경/개선" (수정), "~를 수정" (버그), "~를 제거" (삭제), "~를 리팩터링" (구조 변경)

**예시**:
- `콤보 시스템을 어빌리티 자체 관리로 리팩터링`
- `가드 어빌리티 구현 및 HitReact 가드 분기 추가`
- `프로젝트 구조 분석 보고서 추가`

### 4단계: 그룹별 스테이징 및 커밋

2단계에서 정한 커밋 순서대로, 각 그룹에 대해 다음을 **반복**하라:

- `.env`, 자격 증명 파일 등 민감한 파일이 포함되어 있지 않은지 확인하라.
- **해당 그룹에 속한 파일만** 경로를 명시해 `git add`하라. `git add -A`나 `git add .`는 사용하지 마라.
- 경로에 `Tests/` 폴더가 들어간 파일(임시 검증 테스트)은 어느 그룹에도 넣지 않는다.
- `git status`로 의도한 파일만 스테이징됐는지 확인한 뒤 커밋하라.
- 한국어 커밋 메시지를 UTF-8 임시 파일에 저장하고 `git commit -F <메시지 파일>`로 커밋하라. Bash HEREDOC이나 PowerShell here-string 등 현재 셸에 맞는 저장 방법을 사용한다.
- 시작할 때 이미 다른 그룹의 변경이 스테이징되어 있으면 그대로 섞어 커밋하지 않는다. 기존 인덱스의 파일·부분 스테이징 상태를 보존하면서 해당 그룹만 커밋하고, 커밋 뒤 나머지 스테이징이 유지됐는지 확인한다.

모든 그룹을 각각 커밋할 때까지 반복한 뒤 5단계로 진행하라.

### 5단계: 푸시

- 현재 브랜치와 푸시 대상을 확인한다. detached HEAD거나 원격을 정할 근거가 없으면 임의의 브랜치에 올리지 말고 필요한 정보를 알린다.
- upstream이 있으면 해당 원격의 정보를 `git fetch <원격>`으로 갱신하고, `git rev-list --left-right --count 'HEAD...@{upstream}'`으로 로컬 전용 커밋과 원격 전용 커밋 수를 확인한다. 명령 실패를 0건으로 처리하지 않는다.
- 로컬 전용 커밋이 있으면 `git push`한다. 원격에도 별도 커밋이 있어 거절되면 분기 상태를 보고하며 강제 푸시하지 않는다.
- 로컬 전용 커밋이 0개면 푸시할 커밋이 없다고 보고한다. 원격 전용 커밋이 있으면 뒤처진 상태도 알린다.
- upstream이 없으면 원격과 브랜치명을 확인한 뒤 `git push -u origin <브랜치명>`으로 최초 푸시한다. upstream이 없다는 사실을 미전송 커밋 0개로 취급하지 않는다.
- 새 커밋 생성 여부와 관계없이 실제 푸시의 종료 코드를 확인한다. 실패한 푸시는 성공으로 보고하지 않는다.

### 6단계: 결과 보고

새로 생성한 커밋과 이전부터 있던 미전송 커밋을 구분하고, 전송한 커밋의 해시·메시지와 실제 푸시 결과를 보고하라. 새 커밋 없이 기존 커밋만 푸시한 경우도 결과를 남긴다.
분리 커밋한 경우 각 커밋이 어떤 논리 그룹에 해당하는지 함께 밝혀라.
`Tests/` 폴더라서 올리지 않은 파일이 있으면 작업 트리에 남은 임시 테스트이므로 경로를 함께 알려라.
