# 원격 저장소에 커밋 및 푸시

변경 사항을 커밋하고 원격 저장소에 푸시하라.

## 절차

### 1단계: 변경 사항 확인

다음을 병렬로 실행하라:
- `git status` 로 변경/추가/삭제된 파일 목록 확인
- `git diff` 와 `git diff --staged` 로 변경 내용 확인

변경 사항이 없으면 "커밋할 변경 사항이 없습니다"를 출력하고 종료하라.

### 2단계: 변경 분석 및 논리 그룹화

변경된 파일들을 분석하여 **논리적으로 독립된 변경 단위(그룹)** 로 분리하라.

**1차 기준 — 독립성**: 서로 의존하지 않아 따로 되돌릴 수 있고, 별개의 관심사인가? 이것이 그룹을 가르는 핵심 기준이다.

**보조 신호** (1차 기준이 애매할 때만 참고):
- 변경의 성격 (신규 기능, 리팩터링, 버그 수정, 삭제, 문서/설정 등)
- 다루는 시스템·기능 영역 (예: 데미지 계산 / AI BT / UI 위젯 / 빌드 설정)

주의: **하나의 응집된 작업은 여러 영역(C++ + 블루프린트 + UI 등)에 걸쳐도 한 그룹**이다. 영역이 다르다는 이유만으로 쪼개지 마라 — 따로 되돌릴 수 있는 별개 관심사일 때만 분리한다.

**판단**:
- 변경이 하나의 논리 단위로만 묶이면 → 단일 커밋.
- 서로 다른 관심사가 섞여 있으면 → **그룹별로 분리 커밋**한다.
- 한 파일이 여러 그룹에 걸치면, 가장 핵심이 되는 그룹에 통째로 포함시키고 그 사실을 커밋 메시지/보고에 명확히 남겨라. (이 환경의 Bash는 비인터랙티브라 `git add -p`는 쓸 수 없다. 정 라인 단위 분리가 필요하면 `git diff -- <file> | git apply --cached` 같은 비인터랙티브 패치를 쓰되, 과하면 통째 포함을 택하라.)
- 커밋 순서는 의존 관계를 따른다 — 베이스가 되는 변경(리팩터 등)을 먼저 두어, 가능하면 각 커밋이 단독으로 빌드되도록 정렬하라.

그룹 분리는 **사용자에게 묻지 말고 스스로 판단해 진행**한다 — 그룹을 따로 제시하거나 승인받는 단계는 없다. 분리 결과(각 커밋이 어떤 그룹인지)는 6단계 보고에서 밝힌다.

### 3단계: 커밋 메시지 작성

각 그룹마다 이 프로젝트의 커밋 메시지 컨벤션에 따라 메시지를 작성하라:

```
변경 내용 요약 (한국어)
```

**규칙**:
- 요약은 한국어로 작성
- 하나의 커밋은 하나의 논리 단위만 설명한다. 한 메시지에 "A 및 B 및 C"처럼 무관한 변경을 나열하지 마라(그건 분리 대상이라는 신호다).
- "~를 추가" (신규), "~를 변경/개선" (수정), "~를 수정" (버그), "~를 제거" (삭제), "~를 리팩터링" (구조 변경)

**예시**:
- `콤보 시스템을 어빌리티 자체 관리로 리팩터링`
- `가드 어빌리티 구현 및 HitReact 가드 분기 추가`
- `프로젝트 구조 분석 보고서 추가`

### 4단계: 그룹별 스테이징 및 커밋

2단계에서 정한 커밋 순서대로, 각 그룹에 대해 다음을 **반복**하라:

- `.env`, 자격 증명 파일 등 민감한 파일이 포함되어 있지 않은지 확인하라.
- **해당 그룹에 속한 파일만** 경로를 명시해 `git add`하라. `git add -A`나 `git add .`는 사용하지 마라.
- `git status`로 의도한 파일만 스테이징됐는지 확인한 뒤 커밋하라.
- HEREDOC 형식으로 그 그룹의 메시지로 커밋하라:

```bash
git commit -m "$(cat <<'EOF'
커밋 메시지
EOF
)"
```

모든 그룹을 각각 커밋할 때까지 반복한 뒤 5단계로 진행하라.

### 5단계: 푸시

- `git push`로 원격 저장소에 푸시하라.
- 현재 브랜치가 원격 추적 브랜치가 없으면 `git push -u origin <브랜치명>`을 사용하라.

### 6단계: 결과 보고

생성한 **모든 커밋**의 해시와 메시지를 순서대로 나열하고, 푸시 결과를 요약하여 보고하라.
분리 커밋한 경우 각 커밋이 어떤 논리 그룹에 해당하는지 함께 밝혀라.
