# 프로젝트 리뷰

지정한 범위의 게임 C++ 코드를 **전부 읽고**, 검증을 통과한 결함만 문서로 남긴다. 변경분만 볼 때는 이 스킬이 아니라 하네스의 일반 코드 리뷰를 쓴다.

핵심 원칙은 세 가지다.

1. **나눠서 전부 읽는다** — 오케스트레이터(이 스킬을 실행하는 너)는 소스를 직접 통독하지 않는다. 범위를 묶음으로 나눠 서브에이전트에 맡기고, 묶음마다 모든 파일을 끝까지 읽게 한다. 서브에이전트를 띄울 수 없는 하네스에서는 묶음을 하나씩 순서대로 처리한다.
2. **반증한 것만 남긴다** — 후보는 찾은 리뷰어가 아니라 다른 검증자가 코드로 반증을 시도한다. 의도된 설계로 기록된 동작은 결함이 아니다.
3. **수정할 것이 먼저 보이게 쓴다** — 확정된 항목은 공통 형식으로 쓰고 중요도·확신도 순으로 정렬한다. 영향과 원인을 이해하는 데 필요한 만큼 설명하되, 🟢 사소 항목은 간결하게 쓴다.

리뷰 중에는 소스·에셋·설정을 고치지 않는다. 눈에 띈 결함도 고치지 않고 문서에만 남긴다.

## 1. 범위 결정

| 인자 | 대상 |
| --- | --- |
| 없음 | `Source/WxGame/`과 자체 플러그인 `Plugins/*/Source/`의 게임 런타임 C++ 소스·헤더 |
| 모듈명 | 플러그인이면 `Plugins/<Name>/Source/`, 소스 모듈이면 `Source/<Name>/` 아래 게임 런타임 C++ 소스·헤더 |
| 경로 | 그 경로 아래 게임 런타임 C++ 소스·헤더 |

- 항상 제외: 배치 파일·스크립트(`BatchFiles/`, `.agents/` 아래 스크립트 포함), 빌드 규칙(`*.Build.cs`, `*.Target.cs`), 에디터·개발 도구 모듈(`Source/WxEditor/` 포함), `*.uproject`, `*.uplugin`, `Config/`, `Intermediate/`, `Binaries/`, `*.gen.cpp`, `*.generated.h`, `ThirdParty/`, 엔진 소스, 원본 기획서. 모듈명·경로를 지정해도 같은 제외 기준을 적용한다.
- 설정·모듈 메타데이터·엔진 소스·에셋은 게임 코드의 동작을 검증하는 근거로 필요한 부분만 참조한다. 제외 대상 자체의 결함은 점검·보고하지 않으며 파일·줄 수와 묶음에도 포함하지 않는다. 목록 추출·엔진 경로 확인·빌드를 위한 기존 배치 파일과 스크립트 실행은 허용한다.
- 리뷰 시작 시 시간(Asia/Seoul)과 기준 커밋(`git rev-parse --short HEAD`)을 한 번 기록하고, 파일명과 문서 상단에 같은 기준 커밋을 사용한다. 작업 트리 변경 여부와 검토에 반영한 미커밋 변경 범위도 문서 상단에 기록한다.
- 기능 폴더를 기준으로 **약 2천 줄 단위 묶음**을 만든다. 관련 폴더는 함께 묶는다(예: `Dialogue`·`Quest`·`Interaction`). 묶음 ID와 파일 목록은 저장소 밖 임시 경로에 JSON으로 둔다.
- 시작 전에 파일 수·줄 수·묶음 수를 사용자에게 알린다.
- AGENTS.md대로 `Export-AbilitySystemLists.ps1`을 먼저 실행해 어빌리티·이펙트·캐릭터 목록을 갱신한다.
- 빌드 확인이 필요하면 `build-doctor`로 증분 빌드를 돌리고 경고를 본다.

## 2. 찾기

### 2.1 묶음 리뷰

묶음마다 리뷰어 하나를 띄우고 아래 지시를 **그대로** 전달한다.

- 묶음의 모든 파일을 끝까지 읽는다. 여러 파일을 한 번에 읽어 도구 호출을 줄인다(80회 안쪽 목표).
- 각 함수의 호출자·피호출자를 범위 밖까지 추적한다. 점검 축은 다음과 같다: 수명(BeginPlay/EndPlay/Initialize/Deinitialize/빙의), 델리게이트·타이머 해제, 서버·클라 분기와 복제, GAS 발동·종료·취소와 태그·GE 적용 순서, null·범위, 엔진 API 의미론, 조기 return으로 건너뛰는 정리 코드.
- 엔진 동작은 추측하지 않고 엔진 소스로 확인한다(엔진 경로는 `BatchFiles/Get-WxEngineRoot.ps1`).
- 에셋 구성은 `Saved/AbilitySystemLists/` 목록과 Content `.uasset` 문자열 검색으로 확인한다.
- 의심되면 확신 "낮음"으로라도 후보를 보고한다(최종 보고서에 실을지는 검증 단계에서 정한다). 개수를 채우지는 않는다.
- 결과: 읽은 파일 / 못 읽은 파일, 후보 목록(제목·중요도·종류·위치·근거 위치·발생 조건·원인·영향·수정 제안·확신), 범위 밖 의심점, 다섯 문장 이내 요약.

리뷰어가 못 읽은 파일이 있으면 그 파일만 다시 맡긴다. 모든 파일이 "읽음"이 될 때까지 다음 단계로 넘어가지 않는다.

### 2.2 횡단 관점

파일 단위로는 안 보이는 결함을 찾기 위해, 관점마다 리뷰어 하나가 모듈을 가로질러 흐름을 추적한다.

- 네트워크·권위·예측(리슨 호스트 이중 실행, 0번 PC 가정, 늦은 접속자 수렴 포함)
- 수명·델리게이트·타이머·GC
- GAS 종단 흐름(공격 판정 → 피해 → 반응·그로기·사망·처형)
- 저장·부활·체크포인트·월드 상태 복원(World Partition 셀 재로드 포함)

### 2.3 기계 검사

1절에서 정한 게임 코드 범위 안에서 AGENTS.md 코딩 규칙 1~3(Wx 접두사, 저작권 첫 줄, 인라인 함수 정의)과 `.cpp`의 익명 namespace·static 자유 함수는 리뷰어에게 맡기지 않고 직접 검색으로 전수 확인한다.

### 2.4 중요도

중요도는 신호등 색 하나로만 표시한다. 별도 등급(P0~P3 등)을 겹쳐 쓰지 않는다.

| 신호 | 의미 |
| --- | --- |
| 🔴 심각 | 크래시·세이브 손상·진행 불가, 주요 흐름의 게임플레이 붕괴, 멀티플레이 주 흐름의 상태 불일치, 구체적 조건의 기능 오류(재현 조건을 댈 수 있어야 함) |
| 🟡 개선 | 드문 조건의 경미한 오류, 현재 에셋에서는 드러나지 않는 결함 |
| 🟢 사소 | 결함은 아니지만 근거가 분명한 품질 개선(규칙 위반, 코드와 어긋난 주석, 죽은 코드, 규칙 중복) |

🔴 안에서 같은 확신도라면 크래시·진행 불가처럼 더 급한 항목을 앞에 두고 본문에 그 이유를 밝힌다.

### 2.5 보고하지 않는 것

- **의도·결정으로 기록된 동작**: 하네스 메모리가 있으면 먼저 읽고, 없으면 git 커밋 메시지·작업 기록·코드 주석·Wiki의 결정 기록을 찾는다. 기획서와 달라도 나중의 결정 기록이 있으면 결함이 아니다.
- **이 프로젝트가 받지 않는 수정 제안**: 요청 없는 에디터 검증기·`IsDataValid` 규칙 추가, AnimBlueprint 수정, BT SimpleParallel, 익명 namespace·static 헬퍼, 새 추상화 계층·전용 서브시스템, 클라 예측·동기화 장치 신설, 엔진이 이미 하는 판정을 되풀이하는 게이트.
- 취향 차이, 함수 길이만을 이유로 한 분리, 아직 구현되지 않은 기획 기능 자체.

## 3. 검증

1. **중복 병합** — 근본 원인과 수정 지점이 같은 후보를 하나로 합치고, 함께 보고한 리뷰어 수를 기록한다.
2. **1차 반증** — 찾은 리뷰어와 다른 검증자가 코드를 직접 읽고 반증을 시도한다. 두 관점으로 본다. 첫째, 코드 경로·엔진 의미론: 다른 곳의 가드, 엔진이 이미 처리하는 동작, 도달 불가 경로가 있는가. 둘째, 실사용 도달성·의도: 현재 에셋에서 쓰이는가, 결정 기록이 있는가, 중요도가 과장됐는가, 수정 제안이 2.5와 충돌하는가. 판정은 확정 / 기각 / 판정 보류 중 하나이고, 틀린 조건·원인·수정 제안은 정정한다.
3. 검증은 후보별이 아니라 **영역별 묶음(5~8건)** 으로 맡긴다. 🟢 품질 후보는 가벼운 모델에 맡겨도 된다.
4. **🔴 후보 2차 검증** — 앞선 판정을 모르는 검증자가 다시 확인한다. 의견이 갈리면 세 번째 검증자가 판정한다.
5. **확신도** — 높음: 코드 경로와 현재 에셋 값만으로 결과가 정해진다. 중간: 실행 순서·타이밍 같은 엔진 동작 추론이나, 에디터에서 직접 열어 보지 않은 에셋 내용에 기댄다.
6. **근거 부족 처리** — "낮음"은 찾기 단계의 후보 표시에만 쓴다. 검증 뒤에도 근거가 부족하면 판정 보류로 남기고, 부족한 증거를 기록한다. 확정 항목의 확신도는 높음·중간만 사용한다.

## 4. 문서

이 스킬 폴더 기준 `reports/ProjectCodeReview_<YYYY-MM-DD>_<기준 커밋>.md`에 쓴다(프로젝트 경로: `.agents/skills/project-review/reports/`). 날짜는 리뷰 시작일을 사용한다. `reports/`가 없으면 생성한다. 같은 이름의 파일이 있으면 덮어쓸지 사용자에게 묻는다.

작성 전에 [보고서 템플릿](assets/project-review-template.md)을 읽고 복사해 채운다. 최상위 구성은 **결과 요약 → 항목별 세부 사항** 순서로 유지한다. 제목·상단 정보·세부 절·표·항목의 형식과 빈 절 처리 방법은 템플릿에서 관리한다. 중요도는 2.4, 판정·확신도는 3절을 따른다.

- 코드 개념은 식별자 이름으로 쓴다(한글 직역 금지).
- 링크는 문서 기준 상대 경로와 `#L줄`로 건다. Git 밖 파일(`Saved/` 등)과 엔진 경로는 링크하지 않고 글자로 쓴다.
- 다 쓴 뒤 모든 링크의 대상 파일과 줄 번호가 유효한지 검사하고, 카테고리별 건수·합계와 확정 항목 수를 중복 병합·검증을 마친 결과 데이터와 대조한다. 상세·기획 확인 필요에 같은 ID가 반복돼도 한 건으로 센다. 기각·판정 보류는 결과 건수에 넣지 않는다. 작성용 주석과 자리표시자가 남지 않았는지 확인한다.

## 5. 마무리

- 임시 파일·중간 결과는 저장소 밖에 두고, 끝나면 휴지통으로 보낸다. 이번 실행에서 생긴 빌드 로그(`Saved/Logs/BuildDoctor/`)도 같다.
- 커밋하지 않는다. 사용자가 확인한 뒤 `push`로 올린다.
- 보고: 문서 경로, 신호별 건수(🔴·🟡·🟢), 먼저 볼 🔴 항목 3~5개, 확인하지 않은 것.

## 규모와 사용량

실측(2026-10-02, 538파일·4만 줄): 2천 줄 묶음 리뷰어 하나가 도구를 150~200회 호출했다. 리뷰어 27명과 후보별 검증자를 한꺼번에 띄우자 1시간 만에 사용량 한도에 걸렸다. 그래서 다음을 지킨다.

- 찾기(2절)와 검증(3절)을 **따로 실행**하고, 단계가 끝날 때마다 결과를 임시 파일에 저장한다. 한도에 걸리면 끝난 결과는 두고 남은 묶음만 다시 돌린다.
- 리뷰어에게 도구 호출을 줄이라고 명시한다(2.1). 검증은 묶음 단위로 맡긴다(3절).
- 동시에 띄우는 에이전트 수는 하네스 한도에 맞춰 줄이고, 줄이더라도 모든 파일 읽기는 유지한다.
