## 판단

**도입을 권장한다. 첫 범위는 전투 기획·구현의 연결과 미결정 사항 추적이다.** 기존 문서와 코드를 다시 설명하는 문서 집합보다, “무엇이 요구사항이고, 현재 무엇이 구현됐으며, 어디가 아직 결정되지 않았는가”를 근거와 함께 찾는 기능이 WX에 더 가치 있다.

Markdown과 Git, 기존 파일 검색으로 작은 파일럿을 시작할 수 있다. 전용 검색 서버·벡터 DB·상시 자동화부터 도입할 이유는 아직 없다. 다만 Blueprint와 데이터 에셋까지 포함한 구현 지식, 자동 최신성 보장, 기획 승인 판단은 별도 문제다. Wiki 도입만으로 해결되지 않는다.

## 검토 범위와 한계

- 원문: [Karpathy의 LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f). 댓글에 소개된 도구들은 평가하지 않았다.
- 저장소의 문서·모듈·에셋 목록, 프로젝트 설정, README와 리뷰 표본, 전투 기획과 회의 자료, 관련 C++ 구현을 확인했다.
- 기존 `readme-writer`와 `module-review`의 정의를 운영 설계 비교 자료로 읽었다. 두 스킬을 실행하거나 산출물을 갱신하지 않았다.
- 모든 문서·소스의 전수 의미 검토는 아니다. PDF·PPTX·DOCX·이미지와 Unreal 바이너리 에셋은 목록만 확인했으며, 에디터 실행·빌드·멀티플레이 검증은 수행하지 않았다.
- 작업 트리에 기존 AGENTS/Claude 설정 및 WxDialogue 수정이 있다. 아래 사실은 확인 당시의 작업 트리 기준이며, HEAD만으로 모든 파일의 상태를 재현할 수 있다는 뜻은 아니다. 기존 수정은 건드리지 않았다.

## 원문에서 가져올 부분

원문은 특정 제품의 설치법이 아니라, 원자료에서 읽어 낸 지식을 연결된 Markdown Wiki로 축적하는 패턴이다. 자료 수집, 질의 결과의 재사용, 문서 간 모순·노후화 점검을 운영 흐름으로 제안한다. WX에서는 이를 **원자료 → 근거가 표시된 시스템 설명 → 변경 시 재검토**로 적용하는 것이 적절하다. [원문](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

유지 비용이 사실상 사라진다는 기대는 채택하지 않는다. 생성 비용 외에도 사람의 판정, 잘못된 종합의 수정, 에셋 확인, 변경 영향 추적 비용이 든다. 일반적인 검색도 계속 필요하다. Wiki는 반복 질문의 탐색 범위를 줄이는 역할이며, 코드 수정 전 원본 확인을 대체하지 않는다.

## 이미 발견된 활용 사례

### 1. 같은 문서 안의 기획 불일치

[그로기 피니시 기획서](../../Docs/CombatDesign/그로기_피니시_시스템_기획서.md)의 본문은 가장 가까운 적을 대상으로 삼지만, 흐름도는 락온된 그로기 적을 우선한다. 본문은 적이 PC 근처로 이동한다고 하고, 흐름도는 PC가 이동한다고 한다.

이것은 실제로 확인한 문서 내부 불일치다. Wiki는 임의로 어느 쪽을 채택하지 않고, 두 근거를 나란히 남겨 대상 선정 규칙과 이동 주체를 각각 미결정으로 기록해야 한다. 같은 파일의 본문과 도표도 서로 다른 근거 위치로 취급해야 한다.

### 2. 일반 규칙과 캐릭터별 예외

[핵심 전투 시스템](../../Docs/SystemDesign/Core_Combat_System.md)은 스킬의 MP, 궁극기의 UP 소비 규칙을 설명한다. [9월 19일 회의자료](../../Docs/Meeting/2026-09-19 회의자료.md)는 현광 궁극기 1의 비용을 MP 3, 궁극기 2를 UP 100으로 보고하고, 고유 자원 확대 시 재설계 논의가 필요하다고 적는다.

Wiki에서는 “공통 기획”, “현광 구현 보고”, “일반화 여부 미결정”을 나눠야 한다. 최신 회의자료라는 이유만으로 모든 캐릭터의 규칙을 바꾸면 안 된다. 여기의 수치는 **회의자료에 보고된 값**이며 실제 에셋 값을 검증한 결과가 아니다.

### 3. README와 현재 코드의 차이

[WxCombat README](../../Plugins/WxCombat/README.md)는 네이티브 태그를 직접 선언하지 않는다고 설명하지만, [WxEffect_IgnoreAbilityTags.h](../../Plugins/WxCombat/Source/WxCombat/Public/AbilitySystem/Effect/WxEffect_IgnoreAbilityTags.h)는 `WxCombatGameplayTags::Effect_IgnoreAbilityTags`를 선언한다. [모듈 리뷰](module_review_WxCombat.md)도 이 차이를 지적한다.

README 기준 커밋은 `2872e9a`, 리뷰 기준 커밋은 `fe57e17a`다. Wiki가 README를 그대로 신뢰하면 과거 설명을 재생산한다. README는 탐색 출발점으로 사용하고, 구현 사실은 현재 선언·정의를 확인해야 한다. 리뷰의 개선 제안을 채택된 결정으로 승격해서도 안 된다.

### 4. 동일 원문이 여러 위치에 존재

[SystemDesign/Object_Design.md](../../Docs/SystemDesign/Object_Design.md)와 [LevelDesign/Object_Design.md](../../Docs/LevelDesign/Object_Design.md)는 확인 시 SHA-256이 동일하다.

하나의 내용을 독립적인 두 근거로 계산하지 않아야 한다. 원문을 자동 삭제하거나 이동할 필요는 없다. 두 경로를 하나의 내용 해시에 연결하고, 나중에 서로 달라지면 분기된 자료로 표시하면 된다.

### 5. 기획과 코드 사이의 유용한 연결

[그로기 기획](../../Docs/CombatDesign/그로기_시스템.md)의 게이지 최대치 진입 규칙은 [WxCombatAttributeSet.cpp](../../Plugins/WxCombat/Source/WxCombat/Private/AbilitySystem/Attribute/WxCombatAttributeSet.cpp)의 GP/MaxGP 검사와 연결할 수 있다. [WxAbility_Groggy.cpp](../../Plugins/WxCombat/Source/WxCombat/Private/AbilitySystem/Ability/WxAbility_Groggy.cpp)에서는 서버 권위의 GP 감소 시작, GP 종료 조건, AI 일시정지·재개를 확인했다.

이런 연결은 “그로기 규칙을 바꾸려면 어디를 확인해야 하는가”에 답한다. 다만 몽타주 설정, 개별 캐릭터 부여 여부, 실제 피해 증가량까지 검증됐다는 뜻은 아니다.

## 권장 구조

기존 저장소 안에 `.agents/wiki/`를 추가한다. 아래는 제안이며 이번 검토에서 생성하지 않았다.

```text
.agents/wiki/
  AGENTS.md              # Wiki 작성 범위·근거·갱신 규칙
  index.md               # 사람이 읽는 시작점, 분야별 짧은 안내
  sources.yaml           # 원자료 식별자·경로·해시·종류·확인 범위
  modules/               # 기존 모듈 README 본문을 이관한 정본
  systems/               # 전투 자원, 그로기, 상호작용 등
  workflows/             # 새 캐릭터/적/어빌리티 추가 절차
  decisions/             # 명시적으로 확정된 결정과 대체 이력
  questions/             # 충돌·미결정·확인할 자료
  log.md                 # 수집·갱신·점검 이력
```

원자료는 현재 Docs/Source/Plugins/Config에 둔다. 복제한 raw 폴더를 또 만들지 않는다. 코드와 기획서는 계속 편집되므로, “불변 원자료”는 파일 자체가 아니라 **특정 커밋 또는 내용 해시의 버전**으로 구현한다. 외부 자료를 나중에 수집할 때만 URL·수집일·버전과 허용된 범위의 보관본을 별도로 관리한다.

| 기존 자료 | 책임 | Wiki의 책임 |
| --- | --- | --- |
| 기획서·회의록 | 원래 요구와 논의 기록 | 공통 규칙·예외·변경·미결정 연결 |
| 모듈 README | 이관 후 Wiki로 가는 짧은 안내 링크만 유지하거나 제거 | modules에 모듈 진입점·책임의 정본, systems에 여러 모듈과 기획의 연결 |
| 모듈 리뷰 | 특정 시점의 검토 결과와 개선 제안 | 관련 시스템에서 발견 사항으로 링크 |
| 코드·설정·에셋 | 현재 구현의 근거 | 관찰 범위와 근거 위치를 요약 |
| 기존 스킬 | README/리뷰 등 개별 작업 절차 | Wiki 수집·조회·점검 절차와 연계 |

기존 스킬을 그대로 실행하면 Wiki가 만들어지는 것은 아니다. 특히 두 스킬은 모듈 밖 WxCore/Content 변경의 누락 가능성을 이미 명시한다. Wiki에는 명시적인 원자료 의존 관계가 추가로 필요하다. README 본문 이관 시 readme-writer의 출력 위치·템플릿·변경 감지 규칙도 함께 바꾸거나 해당 생성 경로를 폐기해야 한다.

기존 README의 모듈명만 쓴 이중 대괄호 링크 같은 표기는 실제 파일 경로 링크로 정규화하거나 매핑해야 한다. 같은 이름의 README가 여러 개이므로 파일명만으로 링크 대상을 추측하지 않는다. 기본 링크 형식은 상대경로 Markdown으로 통일하고, 특정 문서 앱은 선택 사항으로 둔다.

### README 통합에 대한 수정 권고

모듈 설명의 본문은 Wiki에 통합하는 편을 권장한다. README와 Wiki에 책임·핵심 타입·확장 절차를 각각 유지하면 두 설명의 최신성을 관리해야 한다. 기존 모듈 README 내용을 `modules/WxCombat.md` 같은 페이지로 이관하고, 시스템 페이지에서는 이를 링크한다. 모듈별 탐색 구조는 보존하되 본문 정본은 한 곳으로 만든다.

루트 README는 프로젝트 소개와 Wiki 시작 링크를 제공하는 입구로 유지한다. 모듈 README는 폴더에서 찾아오는 독자를 위한 링크 한두 줄만 남길 수 있다. 외부에서 개별 플러그인을 떼어 사용하는 요구가 없다면 모듈 README를 제거해도 된다. 안내 파일에는 기술 설명이나 수치를 중복하지 않는다.

이관 절차는 기존 README별 정보 목록 작성 → 현재 코드와 대조 → Wiki로 본문 이관 → 기존 링크와 스킬 갱신 → 누락·깨진 링크 검사 → 기존 본문 제거 순서다. 문서의 과거 기준 커밋을 보존하고, 재검토하지 않은 내용을 이관일 기준 최신으로 표시하지 않는다. 기존 README는 이관 입력 자료가 되지만, 이관 후 Wiki의 영구 근거는 코드·설정·기획 등 원자료에 직접 연결한다.

모듈 리뷰는 과거 시점의 평가 기록이므로 현재 구조 설명과 합쳐 쓰지 않는다. 필요하면 나중에 Wiki 내부 reviews로 위치를 통합하되 검토 시점·미검증 범위·제안 상태를 유지한다. 기획서·회의록 역시 Wiki의 요약으로 대체하거나 삭제하지 않는다.

이 수정 권고는 사용자의 README 통합 질문을 반영한 설계 제안이다. 이번 검토에서 기존 README 삭제·이관 또는 스킬 변경은 실행하지 않았다.

## 믿을 수 있는 지식으로 만들기 위한 규칙

**문장별 성격과 페이지의 최신성을 분리한다.**

- 요구사항: 기획에 이렇게 명시됨. 승인 근거가 없으면 승인 상태 미확인.
- 구현 관찰: 이 버전의 코드 또는 추출된 에셋에서 확인됨.
- 결정: 담당자가 선택했다는 명시적 기록이 있음. 단순 제안이나 회의 개최는 결정의 증거가 아님.
- 추론: 여러 자료에서 도출했지만 직접 확인되지 않음.
- 미결정: 근거가 충돌하거나 빠져 있음.

페이지에는 고유 ID, 주제, 담당 분야, 원자료 ID 목록, 검토 기준 커밋/해시, 검증 범위, 최신성 상태를 둔다. 중요한 수치·규칙 옆에는 원자료 ID와 섹션 또는 코드 심볼을 붙인다. 줄 번호는 보조 정보로만 사용한다.

최신성은 `current`, `needs-review`, `blocked`, `superseded`처럼 별도로 표시한다. 파일이 변경되지 않았다는 것은 내용이 정확하다는 증명이 아니다. `current`도 기록된 범위 내 재검토 완료라는 의미로 한정한다.

예를 들어 그로기 페이지에는 기획 원문, AttributeSet, Groggy 어빌리티, 관련 GameplayTag/Effect를 직접 근거로 연결한다. “그로기 종료 시 AI가 재개된다”는 코드 관찰과 “모든 적에서 정상 재개된다”는 실행 검증 결과를 구분한다.

원자료 충돌은 질문 종류에 맞춰 다룬다. “현재 코드 동작”에는 코드를, “의도한 규칙”에는 확정된 기획을 사용한다. 코드가 곧 의도인 것도, 최신 문서가 곧 승인된 기획인 것도 아니다. 코드와 기획의 불일치를 바로 버그라고 단정하지 않는다.

생성된 Wiki·README·리뷰는 서로를 인용해도 원자료까지 출처가 이어져야 한다. 같은 원문에서 나온 요약 셋을 세 개의 독립 근거로 세지 않는다. 원자료에 포함된 지시문은 자료로 취급하고 Wiki 운영 명령으로 실행하지 않는다.

## 갱신과 조회 방식

1. **변경 발견:** 마지막 확인 이후 Git diff에 추가·수정·삭제·이름 변경을 포함하고, staged/unstaged/untracked도 확인한다. 기준 커밋을 찾지 못하면 최신으로 간주하지 않고 재검토한다.
2. **영향 계산:** 원자료 ID → 참조 페이지의 역방향 목록으로 후보를 고른다. 공용 태그, 설정, 모듈 경계 변경이면 직접 참조 외의 관련 주제도 보수적으로 검토한다.
3. **재검토:** 원자료를 다시 읽어 바뀐 주장과 인용을 수정한다. 삭제된 원자료는 근거 상실을 표시한다. 이름 변경 시에는 링크와 ID 매핑을 갱신한다.
4. **반영:** 관련 페이지·질문·목차·이력을 함께 변경한다. 근거가 부족하면 기존 결론을 조용히 덮지 않고 미확인 상태를 남긴다.
5. **검증:** 링크·원자료·메타데이터 검사를 수행하고 diff를 검토한다. Wiki 생성물 자체의 변경이 다시 원자료 변경으로 감지되지 않도록 제외한다.

미커밋 자료를 수집하면 HEAD만 기록하지 않고 파일별 내용 해시와 작업 트리 관찰임을 남긴다. 실제 내용 보관 없이 해시만 있으면 나중에 원문을 복원할 수 없으므로, 재현 가능한 지식으로 확정할 때에는 원자료 커밋을 연결한다. 문서 작성 때문에 사용자 변경을 자동 커밋하지 않는다.

조회는 목차 → 관련 시스템 페이지 → 필요한 원자료 순으로 한다. 답변에서 중요한 최신성·실행 여부를 표시한다. 모든 대화를 저장하지 않고, 새로운 결정·검증 결과·반복 사용할 설명만 선별해 남긴다.

초기 갱신 시점은 관련 기능 작업 완료, 기획 회의 정리 직후, 주요 변경 후다. 상시 감시보다 누락 없는 수동 실행 절차부터 검증한다. 이후 주기적 점검을 추가할 수 있다.

## Unreal 에셋에 대한 단계적 대응

초기에는 `.uasset/.umap`을 읽었다고 가정하지 않는다. 관련 에셋 경로만 연결하고 “에셋 내부 미검증”을 표시한다.

다음 단계에서 필요한 에셋 종류에 한해 에디터 또는 Commandlet 등의 추출 방식을 검증한다. 추출 후보는 DataTable 행 값, DataAsset 설정, Blueprint 기본값과 컴포넌트 구성, 어빌리티/몽타주 참조, BT/StateTree 연결 정보다. Blueprint 실행 그래프까지 완전하게 추출된다고 미리 약속할 수는 없다.

추출 결과에는 패키지 경로, 원본 해시, 추출기 버전, 엔진 버전, 추출 시점, 제외된 정보를 남긴다. JSON/텍스트는 원본 에셋의 관측 결과로 관리한다. 에셋 목록·참조만 얻은 경우 실제 동작까지 확인했다고 표현하지 않는다. 최종 동작 판정은 필요한 PIE/멀티플레이 테스트와 연결한다.

캐시·중간 산출물·빌드 로그 전체를 수집 대상에 넣지 않는다. 저장소 밖 채팅·개인 자료·외부 서비스 수집은 별도 범위로 정한다.

## 자동 점검과 사람의 역할

| 구분 | 확인할 것 |
| --- | --- |
| 결정적 검사 | 깨진 링크, 중복 ID, 누락 메타데이터, 존재하지 않는 원자료, 내용 해시 변경, 고아 페이지 |
| LLM 검토 | 문장 간 충돌 후보, 과도한 일반화, 기획과 구현의 구분, 빠진 관련 주제 |
| 사람의 판단 | 기획 승인, 예외의 일반화 여부, 충돌 해소, 설계 변경 선택 |
| 실행 검증 | 실제 수치·에셋 적용, 서버/클라이언트 동작, 타이밍·네트워크 조건 |

LLM 점검은 오류 후보를 찾는 보조 수단이지 완전성 보장이 아니다. 운영 초기에 담당 분야별 확인자를 정한다. 모든 문장 편집에 승인 절차를 붙일 필요는 없지만, 설계 결정을 생성기가 대신 내리게 해서는 안 된다.

동시 작업은 페이지 단위로 분리하고 목차·로그 병합을 한 곳에서 처리한다. 여러 작업자가 공유 파일을 동시에 고치는 방식은 피한다. 원자료 수정과 Wiki 수정은 가능한 한 같은 변경 묶음에서 검토한다.

## 권장 파일럿과 판정 기준

첫 주제는 **그로기·피니시·전투 자원**으로 한정한다. 실제 충돌 사례가 있고, 기획과 C++ 근거를 함께 확인할 수 있다.

1. 원자료 10~15개 정도를 선정하고 성격·버전·확인 범위를 등록한다.
2. 시스템 3개, 확정 근거가 있는 결정 기록, 미결정 목록, 목차를 포함해 5~8페이지 정도로 시작한다. 이 숫자는 운영 제안이며 실측 최적값은 아니다.
3. 아래 실제 질문으로 Wiki 없이 답한 결과와 비교한다.
   - 그로기 진입·종료의 기획과 코드 진입점은 무엇인가?
   - 피니시 대상 우선순위와 이동 주체는 확정됐는가?
   - 현광 궁극기의 자원 예외를 모든 캐릭터에 적용할 수 있는가?
   - WxCombat 태그 정의에 대해 README와 코드는 일치하는가?
   - 현재 답변에서 에셋 확인이 필요한 부분은 무엇인가?
4. 별도 검증 환경에서 근거 수정·삭제·이름 변경, 미커밋 변경, 모순 자료 추가를 시험해 관련 페이지가 재검토 대상으로 잡히는지 확인한다.
5. 실무에서 약 1~2주 사용하며 정확성·탐색 시간·수정 비용을 기록한다. 이는 평가 기간 제안이며 구축 공수 견적이 아니다.

확대 조건은 파일럿의 주요 주장에 원자료 근거가 있고, 알려진 충돌을 숨기지 않으며, 변경된 근거가 재검토 대상으로 잡히는 것이다. 동일 질문 세트의 정답률과 답변 시간, 읽은 파일 수, 사람의 수정 시간, 가능한 경우 토큰 사용량을 비교한다. 절감 효과는 아직 측정하지 않았으므로 수치로 약속하지 않는다.

틀린 답을 빠르게 주거나, README와 Wiki를 이중 수정하는 비용이 탐색 절감보다 크면 주제·페이지 수를 줄인다. 실제 검색 실패가 측정될 때 검색 엔진을 추가 검토한다.

## 도입 순서

첫째, 파일럿의 작성 규칙과 근거 추적을 만든다. 둘째, 기존 README/리뷰와 연결하고 변경 감지·링크 점검을 붙인다. 셋째, 팀의 반복 질문에 맞춰 WxWorld, WxAI, WxDialogue/WxQuest 등으로 확장한다. 넷째, 실제 답변에 필요한 에셋 정보부터 추출한다.

WX의 우선 과제는 자료 부족보다 **서로 다른 시점·목적의 자료가 같은 질문에 서로 다른 답을 주는 문제**다. 이 문제를 드러내고 추적하도록 설계한다면 LLM Wiki의 적용 가치는 높다.
